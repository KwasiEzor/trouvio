## 1. Objectif et critères d'acceptation

**ROADMAP** : « Helpers d'autorisation (`requireUser`, `requireAdmin`, requêtes scopées par `userId`). *Accept.* : tests IDOR — un utilisateur ne peut lire/modifier aucune ressource d'un autre. » **Porte P1** : tests d'autorisation verts, revue `security-reviewer` sans point bloquant.

Critères retenus :
- **A1** — `requireUser()` / `requireAdmin()` pour les Server Components et les Server Actions, `authorizeRoute()` pour les Route Handlers. Comportement défini pour « non connecté », « session invalide » et « non admin ». Échec fermé.
- **A2** — L'identifiant utilisateur des requêtes est un type de marque `UserId`, fabriqué **uniquement** à partir de la session. Une `string` venue du client ne compile pas.
- **A3** — Toute requête sur une table métier à `user_id` passe par `ownedBy(table, userId, …)`. Les tables à `user_id` sont recensées dans un registre gardé par un test de parité.
- **A4** — Matrice IDOR sur vraie base, deux utilisateurs A et B, pour **chaque** table du registre : lecture, modification, suppression, id deviné, id mal formé → aucune ligne de B lue ni touchée.
- **A5** — Session sur vraie base (Better Auth) : jeton forgé, session expirée, supprimée ou d'un utilisateur supprimé → refus. Rôle `admin` retiré → refus à la requête suivante.
- **A6** — Garde-fous ESLint (prouvés par mutation) : ni `src/app`, ni les composants, ni `core/` n'importent le schéma, `getDb`, `pg` ou `drizzle-orm` ; aucun cast `as UserId` hors tests.
- **A7** — `/fil` utilise `requireUser` sans changer de comportement (E2E `auth.spec.ts` vert).
- **A8** — Couverture ≥ 80 % par fichier sur les nouveaux fichiers de `src/lib`.

## 3. Choix de conception

**Contexte d'appel → comportement**

| Contexte | Non connecté, ou session invalide | Connecté, pas admin (`requireAdmin`) |
| --- | --- | --- |
| Server Component, page | `redirect(signInPath ?? "/connexion")` (307) | `notFound()` (404, API stable) |
| Server Action | `redirect` (navigation côté client, ou 303 sans JS) | `notFound()` |
| Route Handler | `401` JSON `{ error: "UNAUTHENTICATED" }`, `Cache-Control: no-store` | `403` JSON `{ error: "FORBIDDEN" }` |

**Portée des requêtes**
- Pas de RLS ni de wrapper CRUD générique : il faudrait des casts (§0).
- Le garde-fou repose sur quatre couches :
  1. le type de marque `UserId`, fabriqué seulement depuis la session ;
  2. le prédicat `ownedBy`, aussi dans les conditions de jointure ;
  3. le confinement ESLint de l'accès aux données ;
  4. le registre gardé par la parité, et le kit IDOR que chaque futur dépôt doit utiliser.
- Les dépôts par domaine (`src/features/<d>/repo.ts` ou `queries.ts`) naîtront avec leurs consommateurs (P5, P6), pas maintenant (Q7).

## 4. Approche

### 4.1 `src/lib/auth/access.ts` (pur)

```ts
const userIdSchema = z.uuid().brand<"UserId">();          // NON exporté : seul ce module fabrique un UserId
export type UserId = z.infer<typeof userIdSchema>;
export type UserRole = (typeof USER_ROLES)[number];
export type CurrentUser = Readonly<{ id: UserId; role: UserRole; email: string; name: string }>;
export type AccessNeed = "user" | "admin";
export type AccessDecision =
  | { ok: true; user: CurrentUser }
  | { ok: false; reason: "unauthenticated" | "forbidden" };
export function decideAccess(session: unknown, need: AccessNeed): AccessDecision;
export const resourceIdSchema = z.uuid();                  // ids de chemin ou de corps, validés avant la base
```

Comportement de `decideAccess` :
- La session est analysée par un `z.object({ user: z.object({ id: userIdSchema, role: z.enum(USER_ROLES), email, name, emailVerified: z.literal(true) }) })`, sans `strict` : les champs en trop sont ignorés et le DTO n'en retient aucun.
- Session absente ou mal formée (id qui n'est pas un uuid, rôle inconnu, email non vérifié) → `unauthenticated`. C'est l'échec fermé (Q4).
- Besoin `admin` avec rôle `user` → `forbidden`.

### 4.2 `src/lib/auth/guards.ts` (serveur)

```ts
type SignInPath = typeof AUTH_PATHS.signIn | typeof AUTH_PATHS.invalidLink;   // constantes : pas de redirection ouverte
export async function requireUser(options?: { signInPath?: SignInPath }): Promise<CurrentUser>;
export async function requireAdmin(): Promise<CurrentUser>;
export async function authorizeRoute(need: AccessNeed):
  Promise<{ ok: true; user: CurrentUser } | { ok: false; response: Response }>;
```

- Chacune lit `getSession()`. Une erreur de base **remonte** : jamais transformée en « non connecté », ce qui éviterait une boucle de redirections et masquerait une panne.
- `requireAdmin` refusé → `logger.warn("accès admin refusé", { userId })`. Identifiant interne seulement, pas de Sentry (Q6).
- Règle d'usage, en commentaire en tête de fichier et dans `api-security.md` :
  - appeler le helper **en première ligne**, hors de tout `try/catch` ;
  - dans les layouts : jamais en seul contrôle (rendu partiel, guide Next) ;
  - `proxy.ts` (P1-05) reste optimiste.
- Pas de `server-only` : le paquet lève une exception sous Vitest. `next/headers` suffit à rendre le module serveur, et le confinement ESLint client existant (`lib/auth` hors `client`) s'applique.

### 4.3 `src/lib/db/owned.ts`

```ts
export const USER_OWNED_TABLES = {
  search_profiles: searchProfiles, offer_scores: offerScores, offer_feedback: offerFeedback,
  applications, deliveries,
} as const;
export type UserOwnedTableName = keyof typeof USER_OWNED_TABLES;
export type UserOwnedTable = (typeof USER_OWNED_TABLES)[UserOwnedTableName];
// Gérées par Better Auth seul ; jamais requêtées par le code applicatif.
export const AUTH_OWNED_TABLES = ["sessions", "accounts"] as const;
export function ownedBy(table: UserOwnedTable, userId: UserId, ...extra: (SQL | undefined)[]): SQL;
```

- `ownedBy` = `and(eq(table.userId, userId), ...extra)`, avec une erreur si le résultat est vide. Le prédicat `user_id` est **toujours** présent, même si `extra` vaut `undefined`.
- Usage attendu dans les futurs dépôts :
  - `where(ownedBy(t, userId, eq(t.id, id)))` ;
  - conditions de jointure entre deux tables possédées, par exemple `leftJoin(offerFeedback, and(eq(offerFeedback.offerId, jobOffers.id), ownedBy(offerFeedback, userId)))` ;
  - `values({ ...input, userId })` à l'insertion ;
  - jamais `userId` dans un `set`.

### 4.4 `/fil`

### 4.5 Garde-fous ESLint

Rappel : en config flat, redéclarer une règle la remplace. Chaque bloc qui redéclare reprend donc les interdits existants.

- **`DATA_ACCESS_PATTERN`** : `{ regex: "(^|/)db/schema$|(^|/)lib/db/(client|owned)$|^(pg|drizzle-orm)(/|$)" }`.
  - Nouveau bloc **placé après le bloc général `src/**`** et avant les blocs spécifiques (observabilité, composants d'auth, qui restent prioritaires et couvrent déjà `db/` par `SERVER_ONLY_PATTERN`).
  - Fichiers : `src/app/**/*.{ts,tsx}`, `src/**/actions.ts`, `src/**/*.action.ts`, `src/features/*/components/**`, `src/features/*/core/**` ; tests exclus.
  - Règle : `no-restricted-imports` avec `ENV_IMPORT_PATHS` + `CN_PATTERN` + `SENTRY_PATTERN` + `DATA_ACCESS_PATTERN`.
- **`USER_ID_CAST_SYNTAX`** : `TSAsExpression > TSTypeReference[typeName.name='UserId']` et `TSTypeAssertion > TSTypeReference[typeName.name='UserId']`.
  - Ajouté au `no-restricted-syntax` du bloc général et des blocs non-tests qui le redéclarent (observabilité, composants d'auth, `client.ts`).
  - Exemptés : les tests (bloc existant) et `src/test/**`, par un petit bloc qui redéclare `ENV_SYNTAX` + `SENTRY_SYNTAX` sans le cast.

## 5. Tests prévus (écrits avant le code)

### Unitaires : `access.test.ts`
- `decideAccess` :
  - `null` ou `undefined` → `unauthenticated` ;
  - utilisateur vérifié, besoin `user` → `ok`, DTO réduit à `id, role, email, name` (aucun champ `session`, `token` ni `image`) ;
  - `user` qui demande `admin` → `forbidden` ;
  - `admin` → `ok` pour `user` et pour `admin` ;
  - `emailVerified: false` → `unauthenticated` ;
  - id non uuid, rôle inconnu (`"superadmin"`), `user` absent → `unauthenticated` ;
  - un rôle injecté hors de `user` (`session.role = "admin"`) est ignoré.
- `resourceIdSchema` : accepte un uuid v4 ; refuse `""`, `"1"`, `"' or 1=1 --"`, un uuid tronqué ou à accolades.

### Unitaires : `guards.test.ts`
- `requireUser` :
  - sans session → `redirect("/connexion")` ;
  - avec `signInPath: invalidLink` → `redirect("/connexion?erreur=lien")` ;
  - session valide → DTO ;
  - session non vérifiée → redirection ;
  - `getSession` rejette → même erreur relancée, aucun `redirect`.
- `requireAdmin` :
  - sans session → redirection vers la connexion ;
  - `user` → `notFound()` et `warn` avec `{ userId }` seul (aucun email dans les journaux, vérifié par `everythingLogged`) ;
  - `admin` → DTO.
- `authorizeRoute` :
  - `"user"` sans session → 401, corps `{ error: "UNAUTHENTICATED" }`, `cache-control: no-store` ;
  - `"admin"` avec un `user` → 403 ;
  - succès → `{ ok: true, user }`.

### Parité (sans base) : `schema.test.ts`
- Tables ayant une colonne `user_id` = noms SQL du registre ∪ `AUTH_OWNED_TABLES`, à l'identique.
- Chaque clé du registre est le nom SQL de sa table.
- Une nouvelle table à `user_id` non recensée fait échouer ce test.
- `seedTwoTenants` est typé `satisfies Record<UserOwnedTableName, …>` : la table doit aussi recevoir un seeder, sinon `typecheck` est rouge.

### Intégration IDOR : `owned.db.test.ts`

`it.each` sur les cinq tables du registre, avec A, B et les offres O1 et O2 :
- **Lecture** : `select … where ownedBy(t, A)` ne rend que les lignes de A.
- **Lecture ciblée** : la clé de la ligne de B (`id`, ou `offerId` pour les tables à clé composée, ou rien pour `search_profiles`) sous la portée de A → 0 ligne.
- **Modification** : `update … where ownedBy(t, A, clé de B)` → 0 ligne modifiée ; la ligne de B est relue sans portée, identique.
- **Suppression** : `delete … returning` sous la portée de A sur la ligne de B → 0 ligne ; la ligne de B existe encore.
- **Id deviné** : un `randomUUID()` → 0 ligne.
- **Id mal formé** : refusé par `resourceIdSchema` avant la base. Contre-épreuve : envoyé tout de même, Postgres répond `22P02` (`error.cause.code`), sans aucune ligne.
- **Extra vide** : `ownedBy(t, A, undefined)` reste scopé (régression de `and()`).
- **Jointure** (`offer_scores` ⋈ `job_offers` ⟕ `offer_feedback`, avec `ownedBy` dans le `ON`) : A ne voit jamais le verdict de B sur O1.

### Intégration session : `access.db.test.ts`

Vraie base, Better Auth, harnais HTTP :
- Le cookie de A donne l'id de A, jamais celui de B. Celui de B donne l'id de B.
- Cookie forgé (jeton aléatoire), ou jeton de A avec une signature altérée → `unauthenticated`.
- Après `/sign-out` de A, le cookie de A est refusé et celui de B reste valide.
- `expires_at` passé en base → refus.
- Utilisateur supprimé (sessions en cascade) → refus.
- Admin (rôle posé en base) accepté pour `admin`, puis `update role='user'` → `forbidden` dès l'appel suivant.
- Si Q3 est **refusée** (endpoints gardés), ajouter :
  - `/revoke-session` avec le jeton de B sous la session de A → B toujours connecté ;
  - `/list-sessions` et `/list-accounts` de A → aucune ligne de B ;
  - `/get-access-token` avec `{ userId: B, accountId: compte de B }` → aucune donnée de B.

### E2E
`auth.spec.ts` existant, sans changement :
- `/fil` sans session → `/connexion` ;
- lien invalide → `/connexion?erreur=lien`.

Relancé par l'utilisateur.

### Couverture
`access.ts`, `guards.ts`, `owned.ts` ≥ 80 % par fichier (visé : 100 %). Pas de seuil sur `src/app`.

## 8. Questions ouvertes (une recommandation tranchée par question)

- **Q1 — Non-admin.** Page ou action → `notFound()` ; Route Handler → `403`. **Recommandé.**
  - `forbidden()` est expérimental (drapeau `authInterrupts`).
  - Masquer l'existence de l'API n'a pas de sens : le dépôt est public (ADR 0009).
  - Alternative écartée : `redirect("/fil")`, qui laisse croire à un succès.
- **Q2 — Mécanisme de portée.** `UserId` de marque + `ownedBy` + confinement ESLint + registre et kit IDOR, consignés dans un **ADR 0014**. **Recommandé.**
  - Écartés : le wrapper CRUD générique (casts requis, §0) et la RLS Postgres maintenant.
  - La RLS imposerait une transaction et un `set_config` par requête, ainsi qu'un rôle `BYPASSRLS` pour le job. À réévaluer en P10-01.
- **Q3 — Endpoints Better Auth sans fonctionnalité.** Ajouter à `DISABLED_PATHS` : `/list-sessions`, `/revoke-session`, `/revoke-sessions`, `/revoke-other-sessions`, `/update-session`, `/list-accounts`, `/account-info`, `/get-access-token`, `/refresh-token`. **Recommandé.**
  - Moindre surface : `/list-sessions` expose les jetons de toutes les sessions au JavaScript.
  - Le test « routes désactivées » de P1-02 les couvre automatiquement.
  - À rouvrir, avec leurs tests IDOR (§5), quand une fonctionnalité les demandera (« déconnecter mes autres appareils »).
  - Si refusé : garder ces endpoints et écrire les quatre tests HTTP du §5.
  - Ligne à ajouter dans SECURITY §3.
- **Q4 — `emailVerified` exigé dans `decideAccess`** (défense en profondeur, alors que Better Auth n'ouvre aujourd'hui de session qu'après vérification) : **oui**. Ça ne coûte rien et ça protège contre une évolution de P1-06.
- **Q5 — `authorizeRoute` dès maintenant**, sans consommateur avant P7-04 ou P8-01 : **oui**. Une quinzaine de lignes testées, et une seule façon sanctionnée de répondre 401 ou 403. Sinon chaque route réinventera la sienne.
- **Q6 — Journaliser les refus admin** : **oui**, en `warn` avec `userId` seul (pas de Sentry). Les refus « non connecté » ne sont pas journalisés : trop de bruit.
- **Q7 — Dépôts par domaine** (`search_profiles`, `applications`…) : **non, pas maintenant**. Ils naîtront avec P5 et P6, chacun avec ses tests IDOR par le kit. Les écrire maintenant ferait du code mort et figerait des formes que l'interface dictera.

**Décisions (2026-10-08)** : l'utilisateur a délégué le choix ; toutes les recommandations sont retenues.
