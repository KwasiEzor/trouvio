# P0-06 — `lib/logger` (JSON structuré, sans PII) et Sentry

**Statut** : terminé (2026-09-29 ; voir « Réalisé ») · validé le 2026-09-28 (D1 Sentry 11.0.0, D7 `compiler.define`, D16 aucun `console.*`, D5/D12/groupe Dependabot/projet `trouvio-dev` dans l'organisation `ezor-kwasi` (UE) acceptés) · **Date** : 2026-09-28 · **Branche** : `feat/P0-06-logger-sentry` · Plan produit par l'agent `architect` (versions npm revérifiées : `@sentry/nextjs` 11.0.0 publié le 2026-09-23).

## Objectif et critères d'acceptation
ROADMAP : « `lib/logger` (JSON structuré, sans PII) et Sentry. *Accept.* : une erreur volontaire lancée en local remonte dans le projet Sentry de développement. »

Livrables :
- **Logger** :
  - une ligne JSON par événement, masquage récursif des données sensibles ;
  - erreurs sérialisées avec leur chaîne `cause`, niveau réglé par l'environnement ;
  - sans dépendance à Next.js (réutilisable par le job P5) ;
  - seul moyen légitime de journaliser dans `src/`.
- **Sentry serveur (Node) et navigateur** :
  - collecte minimale et explicite, nettoyage par `beforeSend` et `beforeBreadcrumb` ;
  - ni replay ni traces ;
  - aucun secret exigé en CI (pas d'upload de source maps, pas de `SENTRY_AUTH_TOKEN`).
- **Preuve d'acceptation** :
  - une erreur serveur et une erreur navigateur lancées en local ;
  - retrouvées dans le projet Sentry de dev via le MCP Sentry (`search_issues`) ;
  - sans email, cookie ni en-tête `Authorization` dans l'événement.
- **Porte P0** : CI verte sur `main` ; aucune alerte de sécurité ouverte (`pnpm audit`, dependency-review, CodeQL).

- **pino 10.3.1** :

  - `pino` et `thread-stream` figurent dans les `serverExternalPackages` par défaut de Next ;

## Décisions (Q = question pour l'utilisateur)

**D1 — Q. `@sentry/nextjs` 11.0.0 et `@sentry/core` 11.0.0, versions exactes.**
- Pour : aucun script d'installation, meilleure prise en charge de Turbopack ; la v10 passe en maintenance.
- Prix : une majeure sortie il y a 5 jours, aux valeurs par défaut permissives. D3 les neutralise, avec des tests.
- Alternative : 10.75.3, plus éprouvée, `sendDefaultPii` à `false` par défaut, mais `postinstall` de `@sentry/cli` à autoriser.
- Dependabot : groupe `sentry` (`@sentry/*`) placé avant les groupes génériques, pour que `nextjs` et `core` ne divergent pas. Confirmation humaine requise (fichier de `.github/`).

**D2 — Logger maison, sans dépendance, plutôt que pino.**
- Masquage de clés à toute profondeur et de motifs dans les valeurs (pino ne fait ni l'un ni l'autre).
- Volume minuscule, pas de worker ni de paquet externe à gérer dans le bundle.
- Même code pour le serveur, le job et les tests.
- Environ 200 lignes en 3 modules purs.

**D3 — Collecte Sentry minimale et explicite, identique serveur et navigateur, en défense en profondeur.**
- `dataCollection` posé en entier :

  | Clé | Valeur |
  |---|---|
  | `userInfo` | `false` |
  | `cookies` | `false` |
  | `httpHeaders` | `{ request: { allow: ["user-agent", "content-type", "accept-language"] }, response: false }` |
  | `httpBodies` | `[]` |
  | `urlQueryParams` | `false` |
  | `genAI` | `{ inputs: false, outputs: false }` (offres et critères dès P3) |
  | `databaseQueryData` | `false` |
  | `queues` | `false` |
  | `graphQL` | `{ document: false, variables: false }` |
  | `stackFrameVariables` | `false` (un profil ou un email pourrait se trouver dans une variable locale) |
  | `frameContextLines` | `5` (code public) |

- `beforeSend` = `scrubEvent`, qui réutilise la redaction du logger :
  - supprime `request.cookies`, `request.data` et `request.query_string` ;
  - ne garde que les en-têtes de la liste autorisée ;
  - réduit `user` à `{ id }` ;
  - masque `extra`, `contexts`, `tags`, les messages d'exception et le message de l'événement ;
  - retire la query string de `request.url`.
- `beforeBreadcrumb` masque `message` et `data`, et retire la query string des URL (`fetch`, `xhr`, `navigation`, `http`).
- `dsn` toujours passé explicitement ; **sans DSN, aucun `init`**.
- `environment` = `NODE_ENV`, `debug: false`.

**D4 — Replay désactivé** (jamais de `replayIntegration`).
- Raisons :
  - l'écran porte des critères, des prétentions salariales et un suivi de candidatures ;
  - il faudrait un consentement ;
  - quota de 50 replays ;
  - il faudrait `worker-src blob:` dans la CSP.
- À réexaminer à la bêta, par un ADR.

**D5 — Q. Traces désactivées en P0** (`tracesSampleRate` absent, `tracePropagationTargets: []`).
- Rien à tracer avant la base et les sources.
- Surface de données plus large avec les spans.
- Pas d'en-tête `sentry-trace` envoyé à France Travail ou à Adzuna.
- La contrainte réelle est le quota de 5 000 erreurs. Il est protégé par la déduplication, une limite de débit sur la clé et une capture par source en échec (P5).
- Alternative : 0,1 en production, à trancher en P10-02.
- En conséquence, `buildTimeInstrumentation: false` et `routeManifestInjection: false`. Le second publierait sinon la liste des routes, `admin` comprise, dans le bundle client.

**D6 — `withSentryConfig` dès maintenant, sans upload de source maps.**
- Options : `sourcemaps: { disable: true }`, `telemetry: false`, `silent: true` ; ni `org`, ni `project`, ni `authToken`.
- Le build des PR n'exige **aucun secret**, et aucun `.map` n'est servi (vérifié en E2E).
- L'upload, avec un jeton de build en production seulement, est reporté à P10-02.
- La validation au démarrage reste dans notre fonction de config enveloppée.

**D7 — Q. DSN publié au navigateur par `compiler.define`.**
- Fonctionnement :
  - une seule variable `SENTRY_DSN`, validée dans `env.ts` ;
  - `next.config.ts` l'expose sous l'identifiant `__TROUVIO_SENTRY_DSN__` ;
  - `src/lib/observability/public-config.ts` la lit avec la garde `typeof … !== "undefined"` ;
  - le type est déclaré dans `src/types/globals.d.ts`.
- CLAUDE.md §5 reste vrai : aucun `process.env` hors `env.ts`, aucun `NEXT_PUBLIC_*`.
- Le DSN est public par conception : il ne permet que d'envoyer des événements.
- Limites : la valeur est figée au build ; en production (P10-02), le DSN doit être présent au build.
- Alternatives :
  - (b) `NEXT_PUBLIC_SENTRY_DSN` et `src/lib/env.public.ts` exempté du lint, ce qui demande d'amender CLAUDE.md §5 ;
  - (c) pas de Sentry navigateur avant P6.

**D8 — Format du journal.**
- Une ligne `JSON.stringify` par événement, ce qui neutralise l'injection de lignes.
- Champs fixes : `time` (ISO), `level`, `msg`, `service: "trouvio"`, `runtime` (`web` | `job`).
- `ctx` (contexte et liaisons de `child()`, masqués) est imbriqué, donc aucune collision avec les champs fixes.
- `err` porte l'erreur sérialisée.
- `debug` et `info` vont sur stdout, `warn` et `error` sur stderr.
- Le logger ne lève jamais d'exception, même si la sortie ou le signalement échoue.

**D9 — Redaction par liste de refus, sur les clés et sur les valeurs.**
- Une liste d'autorisation de clés bloquerait chaque nouveau champ et ne protégerait pas les messages d'erreur. Or les fuites réelles passent par les **valeurs** : URL Adzuna avec `app_key`, URL Telegram `bot<TOKEN>`, emails dans un message.
- **Clés**, normalisées en minuscules, sans `-` ni `_` :
  - par inclusion : `password`, `passwd`, `secret`, `token`, `authorization`, `cookie`, `apikey`, `appkey`, `email`, `phone`, `iban`, `session`, `signature`, `dsn`, `credential` ;
  - par égalité : `key`, `pwd`, `auth`, `ip`, `ipaddress`, `address`, `firstname`, `lastname`, `fullname`, `name`, `salary`, `cv`, `resume`.
- **Valeurs** (chaînes, messages et piles) :
  - emails, `Bearer …`, JWT, `sk-ant-…` ;
  - `://user:pass@` ;
  - jeton de bot Telegram `\d+:[\w-]{30,}` ;
  - paramètres de query string sensibles : `token`, `key`, `app_key`, `app_id`, `secret`, `password`, `code`, `signature`, `access_token`, `api_key`.
- **Garde-fous** :
  - `WeakSet` contre les cycles (`"[Circulaire]"`) ;
  - profondeur maximale 8, tableaux coupés à 50, chaînes coupées à 2 000 caractères ;
  - `bigint` en chaîne, `Date` en ISO ; fonctions et symboles retirés.
- Marqueur : `"[REDACTED]"`.

**D10 — Sérialisation des erreurs.**
- Champs : `name`, `message` et `stack` masqués.
- `cause` récursive jusqu'à 5 niveaux ; `errors` pour une `AggregateError`.
- Propriétés propres (`code`, `status`…) masquées.
- Une valeur lancée qui n'est pas une `Error` donne `{ name: "NonError", value }`.
- `EnvValidationError` passe telle quelle (elle ne contient que des noms).

**D11 — `logger.error` signale toujours à Sentry.**
- Avec `err` : `captureException(err, { contexts: { log: ctx } })`. Sans `err` : `captureMessage(msg, "error")`. `warn` ne signale jamais.
- Source : `@sentry/core`, pour que le job P5 (`@sentry/node`) réutilise le logger sans Next. Sans client initialisé, l'appel est sans effet.
- Le signalement est injectable dans `createLogger`.
- Un test vérifie que `SDK_VERSION` est identique entre `@sentry/core` et `@sentry/nextjs`.
- Règle : « journaliser OU relancer, pas les deux » ; la déduplication de Sentry couvre le reste.

**D12 — Q. `userId` (UUID interne) en clair dans `ctx` et `Sentry.setUser({ id })`, jamais d'email.**
- Un UUID aléatoire est une donnée pseudonyme (SECURITY §3).
- Un hachage sans clé n'apporte rien ; un hachage avec clé empêche le lien avec la base (support, demandes RGPD).
- Pour P5 : **les journaux GitHub Actions d'un dépôt public sont lisibles par tous**, donc le job ne journalisera que des agrégats (décision en P5-01).

**D13 — `LOG_LEVEL` dans le domaine `core`.**
- Valeurs `debug | info | warn | error | silent`, `info` par défaut, validé au démarrage.
- `vitest.config.ts` fixe `test.env.LOG_LEVEL = "silent"`.

**D14 — Domaine `sentry` ajouté à `STARTUP_DOMAINS` (web et job).**
- Le DSN reste optionnel, mais un DSN **invalide** empêche le démarrage au lieu de désactiver Sentry sans rien dire.
- Schéma resserré : `https:`, clé publique en nom d'utilisateur, chemin `/<id numérique>`.

**D15 — Runtime Node uniquement, pas de `sentry.edge.config.ts`.**
- Pas de route edge, et `proxy.ts` tourne sous Node en Next 16.
- `register()` charge la config serveur si `isNodeRuntime()` (utilitaire ajouté à `env.ts`, qui lit `NEXT_RUNTIME`).
- La règle est notée dans ARCHITECTURE.

**D16 — Q. `no-console` resserré dans `src/` : plus aucun `console.*`.**
- Le hook `guard-code` reste inchangé.
- Alternative : garder `warn` et `error`.

**D17 — Déclencheurs d'essai temporaires, jamais commités.**
- `src/app/essai-sentry/page.tsx` : erreur serveur, plus un `logger.error` avec un faux email.
- `src/app/essai-sentry/client/page.tsx` : erreur navigateur.
- Supprimés après la preuve, `git status` à l'appui.
- Rejeté : une route de débogage commitée, qui serait une surface d'attaque et du code mort.

**D18 — ADR 0010 « Observabilité : logger maison et Sentry à collecte minimale ».**
- Reprend D2 à D7, la région UE et la rétention.
- Ne contredit aucun ADR ; complète l'ADR 0008 (point 4).

## Tests (écrits avant le code)

**`redact`**
- Clés sensibles masquées à toute profondeur, casse et séparateurs ignorés (`Authorization`, `access_token`, `apiKey`, `X-Api-Key`).
- Clés neutres conservées (`source`, `count`, `offerId`, `userId`).
- Valeurs masquées :
  - email dans une phrase, `Bearer`, JWT, `sk-ant-` ;
  - `postgresql://u:mdp@h/db` ;
  - URL Adzuna `app_id`/`app_key`, les autres paramètres conservés ;
  - URL Telegram `bot123:ABC…`.
- Cas limites :
  - cycle, profondeur supérieure à 8, 51 éléments, 5 000 caractères ;
  - `bigint`, `Date`, `undefined`, fonction, symbole, `Map` ;
  - entrée jamais modifiée.

**`serialize-error`**
- `cause` sur 3 niveaux, et boucle de `cause` bornée.
- `AggregateError`.
- Valeurs qui ne sont pas des `Error` : chaîne, objet, `null`.
- `code` et `status` conservés.
- Email masqué dans le message et dans la pile.
- `EnvValidationError` sans valeur.

**`createLogger`**
- Une ligne par appel, qui se parse en JSON ; un `msg` avec `\n` reste sur une ligne.
- Seuils de niveau ; `silent` n'écrit rien.
- `child()` fusionne les liaisons (l'appel l'emporte en cas de conflit) ; `ctx` masqué.
- Signalement :
  - `error` avec `err` appelle `report` une seule fois, avec le contexte masqué ;
  - `error` sans `err` appelle `captureMessage` ;
  - `warn` n'appelle jamais `report`.
- Une sortie ou un `report` qui lève une exception : aucune exception ne remonte.
- Horloge injectée.

**Instance par défaut**
- Niveau lu dans l'environnement ; `LOG_LEVEL=verbeux` refusé.
- `warn` et `error` vont sur stderr.

**`sentry-options`**
- Sans DSN : `undefined`.
- Avec DSN :
  - `dsn` explicite, `dataCollection` **exactement** égal à D3 ;
  - pas de replay, pas de `tracesSampleRate`, `tracePropagationTargets` vide ;
  - `beforeSend` et `beforeBreadcrumb` présents.
- `scrubEvent` : cookies, corps, query string, en-têtes hors liste, `user.email`, `user.ip_address`, `extra`, message d'exception.
- `scrubBreadcrumb` : `fetch` avec `?token=`, console avec un email.

**`env`**
- `LOG_LEVEL` : valeur par défaut et valeur invalide.
- DSN refusé : `http://`, sans clé, chemin non numérique. DSN UE valide accepté.
- `STARTUP_DOMAINS` exacts ; `.env.example` synchronisé.

**`startup.test`**
- Refus au démarrage avec un DSN invalide.
- Build sans exigence de variable.
- `compiler.define` limité aux clés prévues.
- Aucune `SENTINELLE` (fausse valeur secrète placée dans l'environnement) dans la config sérialisée.

**`global-error.test.tsx`**
- `captureException` appelé.
- Texte en français, bouton accessible qui appelle `reset`.

**`sdk-versions.test`** : versions identiques.

**E2E** (build de production sans DSN)

## Risques et mitigations
