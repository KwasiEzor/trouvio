## 1. Objectif et critères d'acceptation (ROADMAP)

« **P1-06** Activation et liens sûrs (revue sécurité de P1-02, I1 et M1). **Bloque P10.** […] *Accept.* : le lien de vérification mène à une page qui exige le mot de passe avant de vérifier (sinon le compte reste non vérifié, et le lien magique révoque le mot de passe du tiers) ; tout lien ne se consomme qu'après un clic (POST) ; tests d'intégration du scénario du tiers (son mot de passe ne connecte plus) et E2E ; seed : ne jamais promouvoir `admin` une ligne qui porte un compte `credential` non créé par le seed, et seed lancé avant toute ouverture publique. »

| Critère | Traitement |
|---|---|
| Le lien de vérification mène à une page qui exige le mot de passe | L'email pointe vers `/activation?token=…`, une page de l'application. Le formulaire envoie `POST /api/auth/verify-email/confirm {token, password}`. `GET /api/auth/verify-email` est fermé (D1, D2) |
| Sans le mot de passe, le compte reste non vérifié, et le lien magique révoque le mot de passe du tiers | Un mauvais mot de passe donne 401, et rien n'est écrit. La page propose alors un lien de connexion à la même adresse. La confirmation du lien magique appelle `revokeUnprovenAccountAccess` (D3) |
| Tout lien ne se consomme qu'après un clic (POST) | L'email pointe vers `/connexion/lien?token=…`, une page en lecture seule. Le bouton envoie `POST /api/auth/magic-link/confirm {token}`. `GET /magic-link/verify` est fermé. Les deux POST passent par `formCsrfMiddleware` (D3, D4) |
| Tests d'intégration du scénario du tiers, et E2E | `auth.db.test.ts` (« pré-détournement par le lien d'activation ») et `tests/e2e/liens.spec.ts` (§6) |
| Seed : jamais de promotion admin d'une ligne qui porte un `credential` | Garde transactionnelle dans `applySeed` : refus et retour à l'état initial, code de sortie 1 (D6) |
| Seed lancé avant toute ouverture publique | Étape du runbook de déploiement (note P10-02), SECURITY et ADR 0017. Le code échoue fermé si l'ordre n'est pas respecté (D6, Q8) |

## 2. Modèle de menace

| # | Menace | Avant | Après P1-06 |
|---|---|---|---|
| T1 | **Pré-détournement par vérification (I1)** : le tiers inscrit `victime@` avec son mot de passe ; la victime clique le lien ; le tiers se connecte | ouvert | Activer exige le mot de passe. La victime ne le connaît pas, donc le compte reste non vérifié et le tiers ne peut pas se connecter (`EMAIL_NOT_VERIFIED`). La victime passe par le lien magique, qui supprime le mot de passe du tiers. **Invariant** : un compte vérifié ne porte qu'un mot de passe connu du titulaire de la boîte |
| T2 | **Connexion forcée** : le tiers envoie à la victime son propre lien magique ; la victime l'ouvre et se retrouve dans le compte du tiers (elle y dépose son CV, etc.) | ouvert (GET) | Un GET ne connecte plus. La page affiche l'adresse du compte (« Tu vas te connecter en tant que … »). Le POST est protégé par `formCsrf` : une page intersite ne peut pas le déclencher |
| T3 | **Scanner d'emails** (Safe Links, antivirus) : son GET consomme le lien magique, ou ouvre une session dans son bac à sable | ouvert | Les pages en GET sont en lecture seule (aucune consommation, aucune session) |
| T3b | Scanner qui exécute le JavaScript **et clique** | — | Résiduel accepté. Activation : impossible sans le mot de passe. Lien magique : jeton grillé, la personne en redemande un. Une session ouverte chez l'éditeur du scanner reste un risque connu, consigné dans l'ADR 0017 |
| T4 | Fuite du jeton (`Referer`, journaux, Sentry, historique) | partiel | `<meta name="referrer" content="no-referrer">` sur les deux pages. Paramètre nommé `token` (déjà masqué par `redact`). Aucun jeton journalisé (test « journaux » étendu) |
| T5 | Activation utilisée pour deviner un mot de passe | — | Il faut un jeton valide (accès à la boîte). Contrôle « déjà vérifié » **avant** le mot de passe. Verrou par compte partagé avec `/sign-in/email`, et règle par IP |
| T6 | Rejeu | — | JWT d'activation rejoué → `EMAIL_ALREADY_VERIFIED`, sans session ni contrôle du mot de passe. Lien magique : consommation atomique |
| T7 | JWT de changement d'email (`updateTo`, `requestType`) présenté à l'activation | — | Refusé par le schéma (et `/change-email` reste fermée) |
| T8 | **Seed** qui promeut admin une ligne inscrite par un tiers | ouvert | Refus transactionnel. Même sans cette garde, T1 corrigé rend la promotion inexploitable : le tiers ne peut ni vérifier ni se connecter, et le lien magique de l'admin le révoque |
| T9 | POST intersite (CSRF) vers les endpoints de confirmation | — | `formCsrfMiddleware` (Fetch Metadata, `Origin`, `Referer`), corps JSON seulement, `SameSite=Lax` |

## 3. Décisions

**D1. Liens d'email vers des pages de l'application, jamais vers `/api/auth`.**
- `sendVerificationEmail` ignore `url` et bâtit `activationUrl(baseURL, token)` = `${APP_URL}/activation?token=…`.
- `sendMagicLink` bâtit `magicLinkUrl(baseURL, token)` = `${APP_URL}/connexion/lien?token=…`.
- `AUTH_PATHS` reçoit `activate: "/activation"` et `magicLink: "/connexion/lien"`.
- `DISABLED_PATHS` reçoit `"/verify-email"` et `"/magic-link/verify"`. `auth.api.*` reste appelable côté serveur, mais rien ne l'appelle.
- `autoSignInAfterVerification: false`, en défense en profondeur (Q9).

**D2. Activation : `POST /verify-email/confirm`** (plugin `confirmed-links`, `src/lib/auth/confirmed-links.ts`).
1. `use: [formCsrfMiddleware]` ; `metadata: { noStore: true }` ; corps validé par Zod `{ token, password ≤ PASSWORD_MAX_LENGTH }`.
2. `verifyJWT(token, ctx.context.secret)`, puis `verificationPayloadSchema` (`email`, `updateTo` et `requestType` absents). Échec → 400 `INVALID_TOKEN`.
3. `findUserByEmail`. Utilisateur absent → 400 `INVALID_TOKEN`.
4. `emailVerified` → 400 `EMAIL_ALREADY_VERIFIED`, **sans regarder le mot de passe**.
5. `checkSignInAccount(limiter, { email })`, le verrou existant (même seau que `/sign-in/email`) → 429 `TOO_MANY_ATTEMPTS`.
6. `findCredentialAccount`. Absent ou sans mot de passe → `password.hash` (pour un temps de réponse comparable), puis 401 `INVALID_PASSWORD`. Mauvais mot de passe → 401 `INVALID_PASSWORD`. Aucune écriture.
7. Succès : `updateUser(id, { emailVerified: true })`, `createSession`, `setSessionCookie`, puis `{ status: true }`.

**D3. Lien magique : `POST /magic-link/confirm`** (même plugin).
- `use: [formCsrfMiddleware]`, `noStore`, corps `{ token }`.
- `consumeVerificationValue(magicLinkIdentifier(token))`, atomique, expiration comprise. `null` → 400 `INVALID_TOKEN`.
- Enregistrement validé par Zod, même schéma strict que Better Auth.
- `findUserByEmail`. Utilisateur absent → `createUser({ email, emailVerified: true, name }, { method: "magic-link" })` (le hook `user.create.before` borne le nom).
- Compte non vérifié → `revokeUnprovenAccountAccess`.
- Puis `createSession`, `setSessionCookie`, `{ status: true }`.

C'est la recopie fidèle de `magic-link/index.mjs` l. 170-206, sur le modèle d'`email-otp` (Q1). `/sign-in/magic-link`, de Better Auth, continue d'émettre le jeton. Le test d'intégration rejoue le jeton de la boîte d'envoi : il garde l'accord sur le format.

**D4. Pages en lecture seule.**

`/activation` (`src/app/(auth)/activation/page.tsx`) appelle `previewVerificationLink(getAuth(), token)` (`src/lib/auth/links.ts`) :
- `invalid` : message « Ce lien n'est plus valable », renvoi vers la connexion ;
- `verified` : « Ton compte est déjà actif », lien « Se connecter » ;
- `pending` : `ActivationForm` avec l'adresse affichée, le champ mot de passe et le bouton « Activer mon compte ». En cas d'échec, l'aide « Ce n'est pas toi qui as créé ce compte, ou tu as oublié ton mot de passe ? » et le bouton « M'envoyer un lien de connexion », qui envoie `POST /sign-in/magic-link` à l'adresse du jeton.

`/connexion/lien` appelle `previewMagicLink` :
- `invalid` : `redirect(AUTH_PATHS.invalidLink)`, le message existant (Q12) ;
- `valid` : `MagicLinkConfirm`, avec « Tu vas te connecter à Trouvio en tant que {email} » et le bouton « Me connecter ».

Après un succès : `router.push(AUTH_PATHS.afterSignIn)` puis `router.refresh()`, comme `SignInForm`. Les deux pages ont `metadata.referrer: "no-referrer"` et `robots: { index: false }`. Elles ne font pas `redirectIfSignedIn` : un clic peut changer de compte, et l'adresse affichée l'annonce.

Les aperçus lisent `auth.$context` : `verifyJWT` avec `ctx.secret`, et `internalAdapter.findVerificationValue` avec un contrôle explicite de `expiresAt` et un schéma Zod. Ni Drizzle, ni `getEnv` hors de `lib/auth/index.ts`.

**D5. Limiteur.** Dans `AUTH_IP_RULES`, `"/magic-link/verify"` devient `"/magic-link/confirm"` (5 / 60 s), et on ajoute `"/verify-email/confirm"` (10 / 300 s, comme `/sign-in/email`). `RATE_LIMITED_PATHS` perd `/verify-email`.

**D6. Seed.** Dans la transaction de `applySeed`, pour chaque entrée `role: "admin"` :
- `SELECT id, role FROM users WHERE email = $1 FOR UPDATE`. Si la ligne existe, que son rôle n'est pas `admin` et qu'elle porte un compte `provider_id = 'credential'`, lever `SeedAdminPromotionError(index)`.
- Après l'upsert, si la ligne n'a pas été insérée par cette requête alors qu'aucune ligne n'avait été vue (insertion concurrente), même refus.
- Tout est annulé. `cli.ts` journalise « seed refusé » avec l'index seulement (jamais l'email) et sort avec le code 1.
- Une ligne déjà `admin` qui porte un `credential` est acceptée : un admin qui s'est donné un mot de passe en P7-02 ne casse pas un seed relancé (Q7).
- « Seed avant ouverture » : étape du runbook (note P10-02), SECURITY et ADR 0017 (Q8).

**D7. Email « compte existant ».** Si `user.emailVerified === false`, un autre texte : « Un compte a été commencé avec cette adresse sans être activé. Pour le reprendre, demande un lien de connexion : il retire tout mot de passe que tu n'aurais pas choisi. » Le texte part au titulaire de la boîte : aucune énumération par l'API (Q6).

**D8. Code mort retiré.**
- `callbackURL` de `SignUpForm` (ne servait qu'au lien de vérification).
- `callbackURL` et `errorCallbackURL` de `MagicLinkForm`.
- Le paramètre `error` de `/fil` (`?error=` de `/verify-email`).
- Commentaire de `SignInForm` mis à jour (`callbackURL` y reste utile à la redirection).
- Commentaire de `access.ts` l. 35-36 mis à jour (P1-06 fait).

## 5. Approche (chaque étape commence par son test rouge)

1. **Spike de types**, dans le bac à sable sans commit. Un plugin minimal `satisfies BetterAuthPlugin` dans `buildAuthOptions` passe `pnpm typecheck`. Vérifier aussi `auth.$context` (`secret`, `internalAdapter`) et les imports de `better-auth/db`, `/cookies` et `/crypto`.
2. **Cœur pur** : `links.ts`, `policy.ts`, `messages.ts`, `emails.ts`, avec leurs tests unitaires.
3. **`link-tokens.ts`** : vecteur connu, calculé à part dans le test (`"abc"` → SHA-256 base64url sans `=`).
4. **Harnais** (`Call.headers`, `confirmMagicLink`, `tokenOf`) et `SERVED_PATHS`. Les tests de `auth.db.test.ts` du §6.2 sont écrits **rouges**.
5. **Plugin `confirmed-links`, configuration et règles du limiteur** : les tests d'intégration passent au vert. `signUpVerified` réécrit, et les suites `access`, `session-refresh` et `rate-limit` restent vertes.
6. **Aperçus** (`links.ts`) avec `links.db.test.ts`.
7. **Composants** `ActivationForm` et `MagicLinkConfirm` (jsdom, `authClient.$fetch` simulé), puis les pages et le nettoyage du D8.
8. **Seed** (D6) : `apply.db.test.ts` et `cli.test.ts` rouges, puis code.
9. **E2E** : `liens.spec.ts`, mise à jour de `auth.spec.ts` et `session.spec.ts`, budget du limiteur recompté. Lancés par l'utilisateur.
10. **Documents** (§7), puis checklist SECURITY §5, revues `code-reviewer` et `security-reviewer`, section « Réalisé ».

**6.2 Intégration, vraie base (`auth.db.test.ts`, `links.db.test.ts`)**

Activation :
- l'email pointe vers `${BASE}/activation?token=` ;
- `GET /verify-email` → 404 (boucle `DISABLED_PATHS`) ;
- bon mot de passe → vérifié, cookie de session, pas de jeton en JSON, `Cache-Control: no-store` ;
- mauvais mot de passe → 401 `INVALID_PASSWORD`, `emailVerified` reste faux, 0 session ;
- jeton altéré → 400 ; jeton expiré (horloge +1 h 1 s) → 400 ;
- JWT signé avec `updateTo` → 400 ;
- compte déjà vérifié → 400 `EMAIL_ALREADY_VERIFIED`, **même avec le bon mot de passe**, 0 nouvelle session ;
- POST avec `Origin: https://evil.example` sans cookie → 403 ; `sec-fetch-site: cross-site` + `mode: navigate` → 403 ;
- corps `text/plain` → refusé.

**Scénario du tiers (I1)** :
1. Le tiers inscrit `victime@example.com` avec `P_tiers`.
2. La victime ouvre l'activation et saisit `P_victime` → 401, toujours non vérifié.
3. Le tiers tente `/sign-in/email` avec `P_tiers` → 403 `EMAIL_NOT_VERIFIED`, pas de session.
4. La victime demande un lien magique et le confirme en POST → session, et la table `accounts` est vide pour elle.
5. Le tiers tente `P_tiers` → 401.
6. Le tiers rejoue le jeton d'activation avec `P_tiers` → 400 `EMAIL_ALREADY_VERIFIED`.
7. Une seule session existe, celle de la victime.

Lien magique :
- l'email pointe vers `${BASE}/connexion/lien?token=` ;
- **`GET /magic-link/verify` → 404, et le jeton reste valable** (le POST connecte ensuite) ;
- POST → session, puis un second POST → 400 ;
- expiré → 400 ;
- deux POST concurrents (`Promise.all`) → exactement une session ;
- adresse inconnue → compte vérifié, nom borné, rôle `user` ;
- admin du seed → garde son rôle ;
- POST intersite → 403.

Aperçus (`links.db.test.ts`) :
- `previewMagicLink(token)` rend l'email du jeton émis par `/sign-in/magic-link` (accord sur le hachage) ;
- après consommation, ou après expiration → `invalid` ;
- `previewVerificationLink` rend `pending`, `verified` ou `invalid` ;
- **deux aperçus de suite n'écrivent ni session ni `emailVerified`**, et le jeton reste consommable.

Limiteur (`rate-limit.db.test.ts`, limiteur réel) :
- 11e `POST /verify-email/confirm` d'une IP → 429 ;
- le verrou par compte est partagé : 10 échecs d'activation, puis `/sign-in/email` → `TOO_MANY_ATTEMPTS` ;
- 6e `POST /magic-link/confirm` / 60 s → 429.

Journaux : le test existant est étendu aux deux POST. Ni email, ni jeton, ni lien.

Routes servies : liste blanche mise à jour.

Seed (`apply.db.test.ts`) :
- un tiers inscrit l'email de l'admin, puis `applySeed` → `SeedAdminPromotionError`, rôle toujours `user`, aucun profil écrit, aucun autre utilisateur du fichier écrit ;
- une ligne `admin` avec `credential` → acceptée (idempotence) ;
- une ligne vérifiée par lien magique sans compte → promue ;
- `role: "user"` sur une ligne avec `credential` → accepté.

`cli.test.ts` : code 1, message sans email.

## 7. ADR et documents

- **ADR 0017 — Liens d'authentification : activation par mot de passe, consommation par POST** (nouveau). Contexte : I1 et M1. Décisions : D1 à D7. Il nomme l'invariant « vérifié ⇒ mot de passe connu du titulaire » et les résiduels T3b et T4. Alternatives écartées :
  - déléguer à l'endpoint GET de Better Auth en interne (en-têtes et redirections à replomber) ;
  - jeton dans le fragment (`#`) (pas d'aperçu côté serveur, donc pas d'adresse affichée contre T2) ;
  - garder le GET filtré par Fetch Metadata (le critère exige POST) ;
  - endpoint d'aperçu `SERVER_ONLY` (une surface de plus pour rien) ;
  - plugin `email-otp` (refonte de l'interface, hors tâche).
- **ADR 0013** : en-tête « complété par l'ADR 0017 » ; décisions 1 et 5 renvoyées vers 0017 ; ligne « Résiduel bloquant pour P10 (P1-06) » retirée des Conséquences.
- **ADR 0015** : décision 3, `/magic-link/confirm` et `/verify-email/confirm`.
- **SECURITY §3** (l. 43-48) : résiduel remplacé par le dispositif. Ajouts : invariant, « seed avant ouverture », garde du seed.
- **ARCHITECTURE** l. 40 (`activation`, `connexion/lien`) et l. 57 (`confirmed-links`, `links`).
- **TESTING** : liste E2E.
- **ROADMAP** : case P1-06 cochée avec le résumé des tests, et notes ajoutées :
  - **P4-03** : lien de désinscription = page + POST (RFC 8058, `List-Unsubscribe-Post`), jamais un GET qui agit ;

## 10. Questions ouvertes (une recommandation tranchée par question)

- **Q1 — Recopier la consommation du lien magique ou déléguer à l'endpoint GET de Better Auth en interne ?** → **Recopier** avec les primitives publiques, sur le modèle `email-otp`. La délégation exige de recopier les `Set-Cookie`, d'intercepter des redirections `302` levées en exception et d'appeler un GET depuis un POST : plus fragile que 30 lignes explicites et testées.
- **Q2 — Afficher l'adresse sur les deux pages (aperçu côté serveur) ?** → **Oui**. C'est la seule parade à la connexion forcée (T2), et elle indique à la victime d'I1 quel compte elle active. Celui qui détient le jeton a déjà accès au compte : rien n'est divulgué en plus.
- **Q3 — Jeton dans la query ou dans le fragment ?** → **Query** (`?token=`). C'est nécessaire à Q2. Déjà masqué par `redact` ; `no-referrer` sur les pages.
- **Q4 — Secours par lien magique depuis la page d'activation, envoyé à l'adresse du jeton sans saisie ?** → **Oui**. C'est le chemin de la victime d'I1 exigé par le critère. Plafond par destinataire inchangé.
- **Q5 — Verrou par compte de l'activation partagé avec `/sign-in/email` ?** → **Oui, même seau** : un devineur ne double pas son budget.
- **Q6 — Variante de l'email « compte existant » pour un compte non activé (D7) ?** → **Oui**. Petit changement qui guide la victime vers le lien magique ; pas d'énumération.
- **Q7 — Portée de la garde du seed : refuser toute ligne avec `credential`, ou seulement une *promotion* (rôle actuel ≠ admin) ?** → **Promotion seulement**, avec contrôle après l'upsert contre une insertion concurrente. Une ligne déjà admin ne peut recevoir un `credential` que de son titulaire. Un seed relancé reste idempotent.
- **Q8 — « Seed avant ouverture » : garde dans le code ou procédure ?** → **Procédure** : runbook P10-02, SECURITY et ADR 0017. Le code échoue fermé : le seed refuse la promotion, et même promu, le compte du tiers ne peut ni s'activer ni survivre au lien magique de l'admin.
- **Q9 — `autoSignInAfterVerification: false` ?** → **Oui**. Sans effet aujourd'hui (route fermée), mais si quelqu'un la rouvre, I1 ne revient pas silencieusement.
- **Q10 — Nouvel ADR ou amendement de l'ADR 0013 ?** → **Nouvel ADR 0017.** Deux décisions de l'ADR 0013 changent, et des flux de la bibliothèque sont remplacés par du code du projet.
- **Q11 — Point de départ de la branche ?** → **`main` après la fusion de P1-05.** Sinon, partir de `feat/P1-05-en-tetes-securite` et rebaser après la fusion (§8).
- **Q12 — Lien magique invalide : redirection ou message sur place ?** → **Redirection** vers `/connexion?erreur=lien`. Un seul texte, une liste fermée, l'E2E existant reste valable.
- **Q13 — Navigation après succès ?** → **`router.push` + `router.refresh`**, comme `SignInForm`.
- **Q14 — Accepter T3b (scanner qui clique) ?** → **Oui**, consigné dans l'ADR 0017. Aller plus loin (saisir l'adresse pour confirmer) coûte en ergonomie pour un risque faible.
- **Q15 — Existe-t-il une base (Neon de développement ou autre) avec des comptes non issus du seed, vérifiés par l'ancien GET ?** → **À confirmer par l'utilisateur.** Recommandation : aucune migration ; si une telle base existe, la vider avant P10.
