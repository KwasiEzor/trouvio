## 2. Décisions

**D1. Stockage : table Postgres `rate_limits` propre au projet, branchée sur Better Auth par `customStorage`.**
- Une seule implémentation pour tous les limiteurs (IP, compte, destinataire). Un seul `INSERT … ON CONFLICT DO UPDATE … RETURNING` atomique par appel, toutes règles comprises. Compteurs persistants aux redéploiements (fenêtres 15 min – 24 h), partagés en cas de multi-instance, testables sur vraie base.
- Écarté : mémoire Better Auth + Postgres (deux mécanismes, remise à zéro au déploiement) ; Redis/Upstash (nouvelle infra, nouveau sous-traitant RGPD).
- Coût : une écriture par requête `/api/auth/*`. Voir R3.

**D2. Clés pseudonymisées.** Clé stockée = `HMAC-SHA256(clé dérivée, "v1" ‖ portée ‖ fenêtre ‖ sujet)` en hex, encodage à longueur préfixée. Clé HMAC dérivée de `BETTER_AUTH_SECRET` (`HMAC(secret, "trouvio:rate-limit:v1")`), sans nouvelle variable. CHECK `key ~ '^[0-9a-f]{64}$'` en base. Rotation du secret = remise à zéro des compteurs, acceptable.

**D3. Résolution d'IP : celle de Better Auth, sans `trustedProxies`.**
- Contrat avec le reverse proxy (vérifié en P10-02) : Caddy ne transmet qu'une valeur de `X-Forwarded-For` ; port de l'application non publié ; essai au déploiement (11 tentatives avec 11 `X-Forwarded-For` forgés → 429).
- Configuration explicite : `advanced.ipAddress = { ipAddressHeaders: ["x-forwarded-for"], ipv6Subnet: 64 }`, sans `disableIpTracking` (interdit par test) ni `trustedProxies`.
- CDN un jour : `trusted_proxies`/`client_ip_headers` côté Caddy. Pas de variable `TRUSTED_PROXIES` maintenant (Q6).
- Croissance des clés : l'adaptateur `customStorage` ramène tout chemin hors d'une liste fixe à un seau unique `autre`.

**D4. Verrouillage par compte.**
- `hooks.before` sur `/sign-in/email`, **avant** vérification du mot de passe, sur l'email normalisé (`trim`, minuscules) : **10 / 15 min** et **30 / 24 h**.
- Toutes les tentatives comptent (atomique, pas de course entre essais parallèles) ; pas de remise à zéro au succès.
- Même réponse que le compte existe ou non : 429, code `TOO_MANY_ATTEMPTS`, `X-Retry-After`.
- Après le contrôle d'origine (pas de verrouillage intersite) ; s'applique aussi à `auth.api.signInEmail`.
- Lien magique laissé ouvert comme secours ; le message d'interface le propose.

**D5. Plafond d'emails par destinataire.**
- `capRecipients(inner, limiter, log)` enveloppe `AuthMailer`. **3 / 15 min** et **10 / 24 h**, tous types confondus.
- Au-delà : envoi **sauté en silence** (promesse résolue, `info` avec le seul `kind`). Une exception dans `sendMagicLink` donnerait un 500 et romprait l'uniformité des réponses (ADR 0013) ; les textes actuels restent vrais.
- Plafond global quotidien (coût Resend) : P4-03 (Q7).

**D6. Refus admin : journaux limités en mémoire.**
- `createLogThrottle({ windowMs: 10 min, maxKeys: 10 000, now })`, pur. `decide()` journalise le premier refus d'un `userId` par fenêtre, puis un `warn` `{ userId, suppressed }` à la fenêtre suivante. Réponse inchangée (404/403).
- Même mécanisme pour le `warn` « limite atteinte » du limiteur, par portée, sans IP ni email.

**D7. Formulaires publics.** Aucun aujourd'hui ; pas d'aide `limitByIp` (code mort). Livré : `RateLimiter` générique, règle dans `.claude/rules/api-security.md`, notes ROADMAP P4-02, P7-01, P9-02, P10-05.

**Règles par IP (clé `ip|chemin`) :**

| Chemin | Règle | Avant |
|---|---|---|
| défaut | 100 / 10 s (explicite) | idem |
| `/sign-in/email` | **10 / 5 min** | 3 / 10 s |
| `/sign-up/email` | **5 / 10 min** | 3 / 10 s |
| `/sign-in/magic-link` | **5 / 10 min** | 5 / 60 s |
| `/send-verification-email` | **3 / 10 min** | 3 / 60 s |
| `/magic-link/verify` | 5 / 60 s (plugin) | idem |

Budget E2E actuel (1 inscription, 2 connexions, 1 lien magique) en dessous.

**Algorithme : fenêtre fixe.** Compteur + `expires_at`. Si `expires_at <= now` : 1 et `expires_at = now + fenêtre` ; sinon `count + 1`, accepté si `count <= max`. Les refus incrémentent. `retryAfter = ceil((expires_at − now) / 1 s)`. Horloge injectée.

**Purge** opportuniste : `purgeExpired(now, 1000)` tous les 100 appels par processus ; erreur journalisée en `warn` puis avalée.

## 3. Migration et retour arrière

- Table `rate_limits` : `key text PRIMARY KEY CHECK (key ~ '^[0-9a-f]{64}$')`, `count integer NOT NULL CHECK (count >= 1)`, `expires_at timestamptz NOT NULL`, index `rate_limits_expires_at_idx`. Contraintes nommées comme dans `db/schema.ts`.
- Pas d'`id` ni de `user_id` ; hors `USER_OWNED_TABLES` (le test de parité du registre doit l'accepter).
- `0002_rate_limits.sql` par `pnpm db:generate --name rate_limits`, purement additive.
- Retour arrière : revenir au commit précédent, puis `DROP TABLE rate_limits;` par nouvelle migration. Aucune donnée de valeur perdue.
- Droits : `trouvio_app` hérite par `ALTER DEFAULT PRIVILEGES` (SECURITY §3), vérifié en test d'intégration.
- Consommation : upsert multi-lignes, **clés triées** (pas d'interblocage), distinctes par appel (fenêtre dans la clé).
- Purge : `DELETE … WHERE key IN (SELECT key … WHERE expires_at < $now ORDER BY expires_at LIMIT $n FOR UPDATE SKIP LOCKED)`.
- Dev : `pnpm db:migrate:local` ; sans la table, `/api/auth/*` répond 500 (échec fermé, à noter dans le README de la base locale).

## 6. Tests prévus, écrits avant le code

**Unitaires**
- `keys` : déterminisme ; portée/fenêtre/sujet/secret différents → clés différentes ; format `^[0-9a-f]{64}$` ; sujet absent de la clé ; `("a|b","c")` ≠ `("a","b|c")`.
- `rules` : instantané lisible de la table.
- `limiter` : refus si une règle refuse ; `retryAfter` = max ; purge au 100e appel ; purge en échec → `warn`, consommation aboutit ; `warn` limité par portée, sans IP ni email.
- `better-auth-storage` : seau nommé ; `/reset-password/abc` et `/xyz` → même seau `autre` ; traduction `{ allowed, retryAfter }`.
- `throttle` : premier refus journalisé ; `suppressed` exact ; taille bornée ; clés indépendantes.
- `capRecipients` : envoi sous le plafond ; au-delà résolution sans envoi, `info` sans destinataire ; casse normalisée ; erreur du transport interne remonte toujours.
- `account-lock` : email absent → aucune consommation ; normalisation ; refus → `APIError` 429 `TOO_MANY_ATTEMPTS`.
- `config` : `enabled` repris ; `customStorage` présent ; `customRules` conformes ; pas de `disableIpTracking` ; pas de `trustedProxies`.
- `index` : `getAuth()` avec `enabled: true` et `customStorage`.
- `guards` : 5 refus → 1 `warn` ; autre utilisateur → son `warn` ; après fenêtre, `suppressed: 4` ; aucun email.
- `messages` : 429 sans code → texte existant ; `TOO_MANY_ATTEMPTS` → texte du compte.

**Intégration (vraie base)**
- `rate-limit-store.db.test.ts` : premier appel `count = 1` ; `max` atteint → refus, `retryAfter ∈ ]0, fenêtre]` ; remise à 1 après fenêtre ; **20 appels concurrents, `max` 5 → exactement 5 acceptés** ; deux règles, un aller-retour ; clé non hex refusée par CHECK ; purge bornée des seules lignes expirées ; rôle applicatif lit/écrit.
- `rate-limit.db.test.ts` (handler HTTP, harnais `rateLimit: true`, horloge injectée) :
  - **Acceptation 429** : 10 `POST /sign-in/email` depuis `203.0.113.7`, le 11e → **429**, `X-Retry-After` > 0, pas de cookie de session, corps attendu.
  - Autre IP et autre chemin non touchés ; acceptée de nouveau après 5 min.
  - `x-forwarded-for` falsifié à deux valeurs : deux chaînes différentes partagent le même seau (`127.0.0.1` en test ; `no-trusted-ip` en production via `vi.stubEnv` si propre, sinon E2E).
  - Compte : 10 tentatives sur un email depuis 10 IP, 11e → 429 `TOO_MANY_ATTEMPTS` ; autre email non touché ; **réponse identique email inscrit / inconnu** ; lien magique servi pour l'email verrouillé ; refus d'origine (403) ne consomment rien ; `auth.api.signInEmail` bloqué.
  - Destinataire : 3 liens magiques depuis 3 IP → 3 emails ; 4e → 200 identique, aucun email ; inscription sur compte existant compte dans le plafond ; autre destinataire non touché.
  - Magasin en panne → 5xx, aucun email, aucune session.
  - Aucune ligne de `rate_limits` ne contient IP ou email.
  - 50 chemins inventés → au plus une ligne `autre` par fenêtre.
- `auth.db.test.ts` inchangé (harnais désactivé par défaut).

**E2E (`tests/e2e/limiteur.spec.ts`, fixture `request`, lancé par l'utilisateur)** : sur build de production, 11 `POST /api/auth/sign-in/email` avec `X-Forwarded-For: 203.0.113.<n>` propre au fichier → le dernier 429. Prouve `enabled` en production, migration et câblage.
