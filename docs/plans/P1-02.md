## 1. Objectif et périmètre

**Objectif** : un visiteur peut créer un compte, se connecter (mot de passe ou lien magique) et se déconnecter ; les sessions vivent en base ; chaque utilisateur porte un rôle `user` ou `admin` que le client ne peut pas choisir.

**Dans le périmètre**

- Configuration Better Auth dans `src/lib/auth`, route `/api/auth/[...all]`.
- Tables `sessions`, `accounts`, `verifications` dans `db/schema.ts`, migration additive `0001`.
- `database` et `auth` dans `STARTUP_DOMAINS.web` ; variables interdites lues par Better Auth.
- Envoi des emails d'authentification par un port, avec une sortie de développement (boîte d'envoi sur disque).
- Interface minimale : `/inscription`, `/connexion`, une page connectée provisoire `/fil` avec « Se déconnecter ».
- Lecture de session côté serveur (`getSession()`).
- E2E inscription, connexion, déconnexion ; job CI `e2e` avec Postgres.
- Script `dev:local` (reporté de P1-01).

**Hors périmètre, et ce que P1-02 laisse prêt**

| Tâche | Ce qui lui revient | Ce que P1-02 lui laisse |
| --- | --- | --- |
| **P1-03** | `requireUser`, `requireAdmin`, requêtes scopées, tests IDOR | `getSession()` typé avec `user.role` ; `/fil` fait un contrôle provisoire à remplacer par `requireUser` ; `sessions` et `accounts` respectent l'invariant `user_id` |

## 4. Approche détaillée

### 4.1 Version et import

- `better-auth@1.7.7` en version exacte. `minimumReleaseAge` (24 h) la refuse avant le 2026-10-01 à 21:31 UTC : **attendre**, ne pas abaisser la garde. Un repli sur 1.7.6 obligerait à revérifier les faits du §0.
- Imports : `betterAuth` de `better-auth` ; `drizzleAdapter` de `better-auth/adapters/drizzle` ; `magicLink` de `better-auth/plugins` ; `nextCookies` de `better-auth/next-js` ; `createAuthClient` de `better-auth/react` ; `magicLinkClient`, `inferAdditionalFields` de `better-auth/client/plugins` ; `getAuthTables` de `better-auth/db`.

### 4.2 Configuration (`src/lib/auth/config.ts`)

Signature : `buildAuthOptions(deps: AuthDeps): BetterAuthOptions`, avec

```ts
type AuthDeps = {
  db: Database;
  baseURL: string; // getEnv("core").APP_URL
  secret: string; // getEnv("auth").BETTER_AUTH_SECRET
  mailer: AuthMailer;
  log: Logger;
};
```

Options retenues (noms vérifiés dans la doc ou la source) :

```ts
{
  baseURL, secret,
  trustedOrigins: [baseURL],
  database: drizzleAdapter(db, {
    provider: "pg", usePlural: true,
    schema: { users, sessions, accounts, verifications },
  }),
  advanced: { database: { generateId: "uuid" } },
  user: { additionalFields: { role: {
    type: [...USER_ROLES], required: false, defaultValue: "user", input: false,
  } } },
  emailAndPassword: {
    enabled: true, requireEmailVerification: true,
    minPasswordLength: PASSWORD_MIN_LENGTH, maxPasswordLength: 128,
    onExistingUserSignUp,           // envoie l'email « tu as déjà un compte »
  },
  emailVerification: {
    sendVerificationEmail, sendOnSignUp: true, sendOnSignIn: true,
    autoSignInAfterVerification: true, expiresIn: 3600,
  },
  session: { expiresIn: 60*60*24*7, updateAge: 60*60*24 },   // cookieCache laissé désactivé
  databaseHooks: { session: { create: { before } } },        // ipAddress et userAgent à null (Q4)
  disabledPaths: ["/update-user", "/change-email", "/delete-user", "/delete-user/callback",
                  "/sign-in/social", "/link-social", "/unlink-account"],
  logger: { level: "warn", log: bridge(log) },
  telemetry: { enabled: false },
  plugins: [ magicLink({ sendMagicLink, expiresIn: 600, storeToken: "hashed" }), nextCookies() ],
}
```

Points d'attention :

- `nextCookies()` reste **le dernier** plugin.
- Pas de `modelName` (incompatible avec `usePlural`).
- Pas de plugin `admin` : son `role` est un texte à virgules, incompatible avec l'enum `user_role`, et il ouvre des routes `/admin/*`.
- `plan` n'est pas déclaré : Better Auth ne l'écrit ni ne le renvoie, donc le client ne peut pas le poser.
- Limiteur intégré laissé à ses défauts (actif en production). Ne pas activer `disableIpTracking` : il le couperait.
- Chemins de `disabledPaths` relevés dans la source ; un test vérifie le 404 de chacun.

### 4.4 Schéma et migration

Trois tables ajoutées à `db/schema.ts`, propriétés aux noms de champs Better Auth, colonnes SQL en snake_case, aides de P1-01 :

- **`sessions`** : `id` ; `expiresAt` (`expires_at timestamptz not null`) ; `token text not null` + `unique("sessions_token_unique")` ; `createdAt` ; `updatedAt` ; `ipAddress text` ; `userAgent text` ; `userId uuid not null → users.id on delete cascade` ; `index("sessions_user_id_idx")`.
- **`accounts`** : `id` ; `accountId text not null` ; `providerId text not null` ; `userId` (cascade) + `index("accounts_user_id_idx")` ; `accessToken`, `refreshToken`, `idToken`, `scope`, `password` (`text`, nuls permis) ; `accessTokenExpiresAt`, `refreshTokenExpiresAt` (`timestamptz`) ; `createdAt` ; `updatedAt` ; `unique("accounts_provider_id_account_id_unique")` sur `(provider_id, account_id)`.
- **`verifications`** : `id` ; `identifier text not null` + `index("verifications_identifier_idx")` ; `value text not null` ; `expiresAt` ; `createdAt` ; `updatedAt`.

Réconciliation avec les conventions de P1-01 :

| Ce que produirait la CLI | Ce que le plan écrit | Motif |
| --- | --- | --- |
| fichier `auth-schema.ts` séparé | tables dans `db/schema.ts` | `rules/db.md` : schéma unique |
| `timestamp(...)` sans fuseau | `timestamptz` | convention P1-01 |
| `.unique()` et index sans nom explicite | contraintes nommées | lisibilité, cohérence |
| relations Drizzle | aucune | `advanced.database.joins` reste à `false` |
| `users` régénérée | `users` intacte | migration additive |

- La contrainte unique sur `accounts` est un ajout du plan (**supposé** compatible : Better Auth ne la déclare pas). Si un test d'intégration la heurte, la retirer avant de générer la migration.
- Pas d'index sur `sessions.expires_at` : aucune purge n'existe encore.
- Migration : `pnpm db:generate` (avec un nom explicite si l'option existe en 0.31.11), jamais éditée ensuite. Additive : aucun `ALTER` sur `users`.
- Retour arrière : `DROP TABLE sessions, accounts, verifications` (aucune donnée à préserver avant M2) ; sur Neon, branche `pre-p1-02`.
- Neon : `ALTER DEFAULT PRIVILEGES` posé en P1-01 donne déjà le DML à `trouvio_app` sur les nouvelles tables. À contrôler par l'utilisateur après `db:migrate:neon`.
- Garde durable : un test compare `getAuthTables(buildAuthOptions(...))` à `db/schema.ts` (§6), et le contrôle de schéma de Better Auth reste actif à l'exécution.

Lit `searchParams` côté serveur et n'affiche qu'un message d'une **liste fermée** (`lien` → « Ce lien n'est plus valable. Demande-en un nouveau. »).

- Composants client dans `src/features/auth/components/` : `sign-up-form.tsx`, `sign-in-form.tsx`, `magic-link-form.tsx`, `sign-out-button.tsx`. Éléments natifs `<label>`, `<input>` stylés par les tokens (focus par contour, règle `ui.md`), `Button` existant. Aucun composant shadcn nouveau, aucun effet Magic UI (ADR 0007).
- Les formulaires passent par `authClient` vers `/api/auth/*` : une seule porte d'entrée, protégée par le contrôle d'origine et le limiteur intégrés. Des Server Actions appelant `auth.api.*` contourneraient ce limiteur.
- `callbackURL` : constantes du code (`/fil`, `/connexion?erreur=lien`), jamais lues dans l'URL.
- Erreurs : `messageForAuthError(code)` (pur, `src/features/auth/core/messages.ts`). Connexion refusée : « Email ou mot de passe incorrect. » Code inconnu : « Une erreur est survenue. Réessaie dans un instant. » 429 : « Trop de tentatives. Réessaie dans un instant. »

### 4.7 Lecture de session côté serveur (`src/lib/auth/session.ts`)

- `getSession(): Promise<Session | null>` : `getAuth().api.getSession({ headers: await headers() })`, enveloppé par `cache()` de React.
- Type `Session` inféré de l'instance (`user.role` compris).
- Dans un Server Component, la session n'est pas prolongée (les cookies n'y sont pas inscriptibles) : le plugin `nextCookies` le gère.

### 4.8 Emails d'authentification

Ce sont des emails transactionnels déclenchés par l'utilisateur lui-même (inscription, demande de lien), jamais un envoi en son nom.

- **Port** (`src/lib/auth/mailer.ts`) :
  ```ts
  type AuthEmailKind = "verification" | "magic-link" | "existing-account";
  type AuthEmail = { kind: AuthEmailKind; to: string; subject: string; text: string; url?: string };
  type AuthMailer = { send(email: AuthEmail): Promise<void> };
  ```
- **Textes** (`src/features/auth/core/emails.ts`, pur) : sujet et corps en français, tutoiement. Chaque email finit par « Si tu n'es pas à l'origine de cette demande, ignore cet email. » Le sujet ne contient jamais le lien.
- **Transport de P1-02 : boîte d'envoi sur disque** (`createOutboxMailer(dir)`) : un fichier JSON par message, dossier en `0700`, fichiers en `0600`, nom `<horodatage>-<kind>-<aléa>.json`. Actif seulement si `AUTH_EMAIL_OUTBOX_DIR` est posée, donc en boucle locale seulement.
- **Sans boîte d'envoi** : `resolveAuthMailer()` rend un transport qui lève `AuthEmailNotConfiguredError`. La route répond par l'erreur générique et journalise une erreur sans donnée. Échec fermé jusqu'à P4-03 (Q1).
- **Tests Vitest** : transport capturant injecté par `createAuth`. Aucun réseau.
- **E2E** : `playwright.config.ts` pose `AUTH_EMAIL_OUTBOX_DIR` vers un dossier temporaire ; `tests/e2e/outbox.ts` attend le fichier destiné à l'adresse du test et en extrait l'URL.
- **Journaux** : `log.info("email d'authentification déposé", { kind, transport })`. Jamais le destinataire, le lien ni le jeton.
- **Dev** : `"dev:local"` dans `package.json`, qui lit `db/local/dev.vars`, fabrique un `BETTER_AUTH_SECRET` aléatoire à chaque lancement et pose la boîte d'envoi sur `.tmp/outbox` (ignoré par git). Forme exacte à valider à l'implémentation ; les sessions de dev tombent à chaque redémarrage, ce qui est accepté.

### 4.9 Journaux et Sentry

- `src/lib/auth/log-bridge.ts` : `bridge(log)` rend la fonction `(level, message, ...args)` attendue par Better Auth.
  - `error` **avec** une instance d'`Error` dans les arguments → `log.error(message, { err })` (Sentry).
  - `error` sans erreur (origine refusée, `callbackURL` invalide) → `log.warn` : une sonde d'attaquant ne doit pas consommer le quota Sentry.
  - Les arguments non-erreurs ne sont pas recopiés ; le message passe par le masquage du logger.
- Résiduel ADR 0012 : masquer l'hôte et l'adresse dans les messages de connexion de `pg` (`getaddrinfo ENOTFOUND <hôte>`, `connect ECONNREFUSED <ip>:<port>`) dans `src/lib/logger/redact.ts`, appliqué par `serializeError` et le `beforeSend` de Sentry.

### 4.10 Rôles et création d'un admin

- Le rôle vit dans `users.role` (enum `user_role`, défaut `user`), colonne existante.
- Un utilisateur ne peut pas se l'attribuer : `input: false` remplace toute valeur envoyée par `"user"`, et `/update-user` est désactivé.
- Un admin est créé **par le seed seulement** (`role: "admin"` dans `db/seed.local.json`, `pnpm db:seed:neon -- --allow-remote` dans le terminal de l'utilisateur). Aucune route ne modifie un rôle.
- Le compte du seed n'a pas de mot de passe : sa première connexion se fait par lien magique, qui marque l'email vérifié et garde le rôle (test dédié).
- Attention, déjà vrai en P1-01 : le seed réécrit `role` à chaque passage.

**ADR 0013 proposé** — « Configuration de Better Auth » : vérification d'email obligatoire (réponses uniformes), rôle par champ `input: false` sans plugin `admin`, appels par le handler HTTP et non par Server Actions, emails par port avec boîte d'envoi limitée à la boucle locale, IP et agent utilisateur non stockés, variables Better Auth interdites.

## 10. Questions ouvertes

- **Q1. Transport des emails en P1-02.**
  - A : boîte d'envoi sur disque seulement ; Resend en P4-03 ; sans transport, échec fermé.
  - B : ajouter dès maintenant un transport Resend par `fetch`.
  - **Recommandé : A.** Resend, ses gabarits et son domaine vérifié appartiennent à P4-03 ; aucun déploiement n'existe avant P10 ; P1-02 est déjà large. Le port rend le branchement trivial plus tard.

- **Q2. CLI Better Auth.** La note ROADMAP demande des tables « générées par la CLI ».
  - A : l'utilisateur lance `pnpm dlx auth@1.7.7 generate` dans son terminal, vers un fichier hors dépôt, puis transcription. Cela impose un fichier de configuration dédié à la CLI et des variables.
  - B : pas de CLI. Tables écrites à la main d'après `getAuthTables` (la source que lit la CLI), gardées par un test de parité permanent et par le contrôle de schéma à l'exécution.
  - **Recommandé : B.** La sortie de la CLI devrait de toute façon être réécrite (fichier séparé, `timestamp` sans fuseau, `users` régénérée) ; B donne une garde durable plutôt qu'une génération ponctuelle, et n'exécute aucun paquet hors bac à sable. C'est un écart à la lettre de la note : à valider, puis corriger la note.

- **Q3. Inscription par lien magique.**
  - A : permise (un email inconnu qui clique crée un compte, nom vide).
  - B : `disableSignUp: true`.
  - **Recommandé : A.** La réponse est uniforme dans les deux cas, l'email est prouvé par le clic, et B mène à une impasse après le clic. Le nom vide se complète en P6-05.

- **Q4. IP et agent utilisateur des sessions.**
  - A : ne rien stocker (colonnes présentes, valeurs nulles).
  - B : stocker.
  - **Recommandé : A.** Minimisation (SECURITY §4), cohérent avec « IP non stockées » de l'ADR 0010 ; aucune fonctionnalité prévue ne les lit. Le limiteur calcule l'IP à la volée et n'en dépend pas.

- **Q5. Longueur minimale du mot de passe.**
