« **P1-05** En-têtes de sécurité (SECURITY §3) : CSP avec nonce (via `proxy.ts`), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors 'none'`. *Accept.* : test vérifiant chaque en-tête sur une page et une route API ; aucun script autorisé par `unsafe-inline`. »

| Point de la tâche ou des notes | Traitement |
|---|---|

## 2. Décisions

**D1. Deux sources d'en-têtes, sans chevauchement.**
- **`next.config.ts` → `headers()`**, sur `/:path*`, toutes routes (pages, API, `_next/static`, `public/`) :
  - `Strict-Transport-Security: max-age=63072000; includeSubDomains`. Pas de `preload` (Q7). Un navigateur l'ignore en HTTP (RFC 6797 §8.1), localhost compris.
  - `X-Content-Type-Options: nosniff`.
  - `Referrer-Policy: strict-origin-when-cross-origin` (Q8).
  - `Permissions-Policy: accelerometer=(), camera=(), display-capture=(), geolocation=(), gyroscope=(), magnetometer=(), microphone=(), midi=(), payment=(), serial=(), usb=()` (Q9).
  - `X-Frame-Options: DENY`, complément historique de `frame-ancestors`.
- **`next.config.ts`**, sur `/api/:path*` : `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`. Les réponses y sont en JSON : rien ne doit s'exécuter.
- **`proxy.ts`**, pages seulement : CSP à nonce, `x-request-id`, prolongation de session.
- **Matcher** : `'/((?!api/|_next/static/|_next/image|icon\\.svg$|brand/).*)'`.
  - Les prefetchs ne sont **pas** exclus. Une requête HTML portant un en-tête `next-router-prefetch` forgé sortirait sinon sans CSP. Le proxy reste pur pour eux, son coût est négligeable.
- **Écarté** : tout faire dans le proxy. Les fichiers statiques n'auraient plus `nosniff` ni HSTS, et le proxy tournerait devant chaque appel `/api/auth/*`.

**D2. CSP des pages** (`buildPageCsp`, pur) :
```
default-src 'self';
script-src 'self' 'nonce-<n>' 'strict-dynamic'          (+ 'unsafe-eval' en dev seulement) ;
style-src 'self' 'nonce-<n>'                              (dev : 'self' 'unsafe-inline') ;
style-src-attr 'unsafe-inline'                            (Q6) ;
img-src 'self' data: blob:;  font-src 'self';
connect-src 'self' [origine Sentry exacte] ;
object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none';
upgrade-insecure-requests                                 (seulement si APP_URL est en https)
```
- **Nonce** : 16 octets de `crypto.getRandomValues`, en base64, un par requête. Le constructeur refuse un nonce hors motif (défense contre l'injection de directives).
- **Rendu dynamique de toutes les pages** : `await connection()` dans `src/app/layout.tsx`, en un seul point (Q5).

**D3. Prolongation de session dans le proxy, en processus.**
- **Principe** : `refreshSession(auth, headers)` appelle `auth.api.getSession({ headers, returnHeaders: true })` et rend les lignes `Set-Cookie`. Le proxy les ajoute à la réponse. Dans le runtime Next, `nextCookies` pose les mêmes cookies par `cookies()`, que l'adaptateur recopie : même contenu, à vérifier en E2E (R3).
- **Conditions** : méthode GET ou HEAD, `getSessionCookie(request)` non nul, `sec-fetch-dest` égal à `document` ou absent. Les navigations RSC et les prefetchs ne déclenchent rien : au plus une lecture de session en base par chargement de page.
- **Échec fermé conservé** :
  - une panne de lecture est rattrapée dans le proxy, avec un `warn` limité par `createLogThrottle`, porteur du `requestId` et sans cookie ;
  - la page continue, et son `requireUser` échoue fermé tout seul ;
  - le proxy ne **décide jamais** d'un accès.
- **Effets de bord** : une session expirée ou un cookie altéré reçoivent le `Set-Cookie` d'effacement de Better Auth.
- **Écarté** :
  - relayer `/api/auth/get-session` en HTTP : saut réseau, limiteur, IP du serveur ;
  - `authClient.getSession()` côté client : JavaScript requis, jeton exposé en JSON, une écriture `rate_limits` par chargement de page (Q1).

**D4. Sentry : `connect-src` avec l'origine exacte de l'organisation.**
- L'origine `https://o<id>.ingest.de.sentry.io` est tirée de `publicSentryConfig().dsn`, la valeur que le bundle navigateur utilise réellement.
- Sans DSN, `'self'` seul. Jamais de joker `*.ingest.de.sentry.io` : il ouvrirait l'exfiltration vers n'importe quelle organisation Sentry.
- **À prouver à l'étape 2** : que `compiler.define` atteint bien le bundle du proxy. Repli si ce n'est pas le cas : `getEnv("sentry").SENTRY_DSN` (R4).

**D5. `/get-session` fermée, jetons retirés.**
- `/get-session` entre dans `DISABLED_PATHS` et sort de `RATE_LIMITED_PATHS` et de `SERVED_PATHS`. `auth.api.getSession` (côté serveur) n'est pas touché.
- ESLint interdit `authClient.useSession` et `authClient.getSession` (`no-restricted-properties`, renvoi à l'ADR 0016).
- Hook `after` (`src/lib/auth/session-token-hook.ts`) sur `/sign-in/email`, `/sign-up/email` et `/magic-link/verify` : `token` passe à `null` et `session.token` est retiré. La forme de la réponse est gardée.
- `config.ts` compose `hooks.after` avec le `before` existant.

**D6. `requestId`.**
- Le proxy génère un UUID, l'écrit en en-tête de requête `x-request-id` (en écrasant toute valeur du client) et le renvoie en en-tête de réponse (utile au support).
- `requestLogger(base = logger)` (`src/lib/http/request-context.ts`) lit `headers()` et valide l'UUID par Zod. Résultat : `base.child({ requestId })`, sinon `base`.
- Il est placé hors de `lib/logger`, que le job P5 utilise sans Next.
- Usage : `decide()` (`guards.ts`), pour le refus admin journalisé.
- `x-request-id` rejoint `ALLOWED_HEADERS` de `sentry-options.ts`, pour relier un événement Sentry au journal.
- Limite : les journaux internes de Better Auth (instance unique) n'auront pas de `requestId`.

**D7. « Déjà connecté ».**
- `redirectIfSignedIn()` : si `decideAccess(await getSession(), "user").ok`, alors `redirect(AUTH_PATHS.afterSignIn)`.
- Une session refusée (email non vérifié, rôle inconnu) ne redirige pas : la boucle avec `requireUser` est impossible. Une panne de lecture remonte, comme dans les autres helpers.

## 5. Tests prévus, écrits avant le code

**Unitaires**

`security-headers` :
- La CSP de production a exactement les directives de D2.
- `script-src`, `script-src-elem`, `script-src-attr` et `default-src` ne contiennent jamais `'unsafe-inline'` ni `'unsafe-hashes'`, en production comme en développement.
- `'unsafe-eval'` n'apparaît qu'en développement.
- `upgrade-insecure-requests` n'apparaît qu'en https.
- Avec le DSN `https://cle@o1.ingest.de.sentry.io/2`, `connect-src` contient exactement `https://o1.ingest.de.sentry.io` : ni clé, ni chemin, ni joker. Sans DSN, `'self'` seul.
- Un nonce hors motif (`a; script-src *`) est refusé.
- Deux nonces successifs diffèrent, avec au moins 22 caractères, conformes au motif de Next.
- `API_CSP` est exacte.
- Par `unstable_getResponseFromNextConfig`, chaque en-tête commun apparaît sur `/`, `/api/auth/ok`, `/_next/static/x.js` et `/brand/trouvio-mark.svg`. La CSP de l'API n'apparaît que sous `/api/`.

`proxy-handler` :
- Une page reçoit une réponse « next ». La CSP de réponse et l'en-tête de requête transmis (`x-middleware-request-content-security-policy`) portent le même nonce.
- `x-request-id` est un UUID, différent de la valeur envoyée par le client, identique en requête et en réponse.
- Sans cookie de session : `refreshSession` n'est pas appelée.
- Cookie présent, GET, `sec-fetch-dest: document` ou absent : appelée, et les `Set-Cookie` sont recopiés.
- `sec-fetch-dest: empty` ou POST : non appelée.
- `refreshSession` en échec : la réponse garde sa CSP, un seul `warn` part, avec le `requestId` et sans cookie ; un second échec dans la fenêtre ne journalise rien.

`proxy` (matcher, `unstable_doesMiddlewareMatch`) :
- Vrai pour `/`, `/connexion`, `/fil`, `/inexistante`, et pour `/fil` avec l'en-tête `next-router-prefetch`.
- Faux pour `/api/auth/ok`, `/_next/static/chunks/a.js`, `/_next/image?url=x`, `/icon.svg`, `/brand/trouvio-mark.svg`.

`session-token-hook` :
- `token` passe à `null` et `session.token` est retiré sur les trois chemins.
- Autre chemin : réponse intacte.
- Réponse non JSON ou nulle : rien ne change.

`request-context` (`next/headers` simulé) :
- UUID valide : un enfant porteur du `requestId`.
- En-tête absent ou invalide : le logger de base.

`guards` :
- `redirectIfSignedIn` : une session valide redirige vers `/fil`.
- Session absente, non vérifiée ou au rôle inconnu : aucune redirection.
- Panne de lecture : l'erreur remonte.
- Le refus admin journalisé porte le `requestId`.

`sentry-options` : `x-request-id` est conservé, les autres en-têtes restent filtrés.

**Intégration** (vraie base, harnais `buildTestAuth`)

`session-refresh.db.test.ts` :
- Session de plus d'un jour (`expires_at` reculé à maintenant + 6 j − 1 min) : `Set-Cookie` de session avec `Max-Age=604800`, `HttpOnly` et `SameSite=Lax`, et la ligne passe à maintenant + 7 j (± 1 min).
- Session de moins d'un jour : aucun `Set-Cookie`, ligne inchangée.
- Session expirée : cookie d'effacement, ligne supprimée.
- Cookie altéré : pas d'exception, pas de session.
- `baseURL` en https : cookie `__Secure-` et `Secure`.
- Harnais avec le limiteur réel : **aucune ligne** dans `rate_limits` après la prolongation.

`auth.db.test.ts` :
- `GET /get-session` répond **404**.
- La réponse de `/sign-in/email` porte `token: null`.
- Lien magique sans `callbackURL` : réponse sans `token` ni `session.token`.
- La liste blanche des routes servies est à jour.

**E2E** (build de production, lancé par l'utilisateur ; `X-Forwarded-For` propre à chaque fichier, budget : 1 inscription par exécution)

`en-tetes.spec.ts` :
- Sur `/connexion` : chaque en-tête et sa valeur exacte, CSP avec nonce.
- Sur `/api/auth/ok` : en-têtes communs et CSP de l'API.
- Sur un script `/_next/static/…` : `nosniff` et HSTS.
- Pour `/`, `/inscription`, `/styleguide`, une page 404 et `/fil` connecté :
  - dans le HTML brut (fixture `request`), chaque balise `<script` porte `nonce="<nonce de l'en-tête>"` ;
  - deux chargements donnent deux nonces différents (preuve du rendu dynamique) ;
  - aucun `securitypolicyviolation` (écouteur posé par `addInitScript`) ni aucune erreur console après l'hydratation.
- `page.addScriptTag({ content: "window.__brecheCsp = true" })` : `window.__brecheCsp` reste indéfini et une violation `script-src` est enregistrée.

`session.spec.ts` :
- Inscription, puis vérification par la boîte d'envoi (session ouverte).
- `vieillirSession`, puis `GET /fil` : la réponse porte un `Set-Cookie` de session (`Max-Age` de 7 jours), et la base passe à maintenant + 7 j environ.
- Second chargement : aucun `Set-Cookie`.
- Connecté, `/connexion` mène à `/fil`.

Les E2E existants (`auth.spec.ts`, `limiteur.spec.ts`, `styleguide.spec.ts`, `observabilite.spec.ts`) deviennent des tests de non-régression de la CSP : les formulaires doivent toujours s'hydrater.

**Preuves par mutation prévues**
- `'unsafe-inline'` ajouté à `script-src`.
- `connection()` retiré.
- Prolongation coupée.
- `/get-session` retirée de `DISABLED_PATHS`.
- Hook `after` retiré.

Chacune doit rendre un test rouge.

## 6. Risques

| # | Risque | Parade |
|---|---|---|
| R1 | Une page redevient statique : scripts bloqués, page cassée en production | `connection()` dans le layout racine ; E2E nonce sur chaque page ; mutation |
| R2 | Une lecture de session en base par chargement de page (plus celle de la page) ; base en panne | Lectures par clé primaire, volume faible ; échec du proxy rattrapé, la page échoue fermé |
| R3 | La recopie des cookies par l'adaptateur Next ou `nextCookies` change à une montée de version (attributs, doublons) | E2E de prolongation : attributs et expiration vérifiés |
| R4 | `compiler.define` n'atteint pas le bundle du proxy : Sentry bloqué sans bruit | Sonde de l'étape 2 ; repli `getEnv("sentry")` ; note P10-02 : DSN identique au build et à l'exécution |
| R5 | Composants qui injectent un `<style>` (Radix Dialog) ou scripts tiers (Stripe) | Notes P6, P7-01, P9 : nonce par `x-nonce` et `setNonce` le moment venu, origines ajoutées à la CSP |
| R6 | Tout en rendu dynamique : TTFB, pas de cache | Volume faible, pas de CDN (ADR 0006) ; mesure Lighthouse en P7-01 |
| R7 | Nom de fonctionnalité inconnu dans `Permissions-Policy` : erreur console | Liste de fonctionnalités établies ; E2E « aucune erreur console » |
| R8 | Besoin futur de `useSession` | Garde ESLint ; réouverture par l'ADR 0016 avec retrait du jeton |
| R9 | Onglet ouvert plus de 7 jours sans rechargement : déconnexion (pas de prolongation en navigation RSC) | Accepté et documenté ; un chargement complet par semaine suffit |
| R10 | `upgrade-insecure-requests` sur `http://localhost` (Safari) | Directive seulement en https |
| R11 | Doc de Next divergente (`unstable_doesProxyMatch`) | Utiliser `unstable_doesMiddlewareMatch` ; noté dans l'ADR |

## 8. Questions ouvertes (une recommandation tranchée par question)

> **Décision de l'utilisateur (2026-10-13)** : toutes les recommandations ci-dessous sont retenues (Q1 A, Q2 A, Q3 oui, Q4 A, Q5 A, Q6 A, Q7 oui, Q8 A, Q9 telle quelle, Q10 P10-02, Q11 oui, Q12 oui, Q13 oui, Q14 oui).

1. **Q1 Prolongation de session.**
   - A) Proxy, `auth.api.getSession` en processus, sur chargement de document avec cookie.
   - B) `authClient.getSession()` dans un composant client de `(app)`.
   - C) Proxy qui relaie `/api/auth/get-session` en HTTP.
   - **Recommandé : A** : sans JavaScript, sans jeton exposé, sans écriture dans `rate_limits`, IP sans objet.
2. **Q2 `/get-session`.**
   - A) Désactivée, avec la garde ESLint.
   - B) Servie, `token` retiré par un hook `after`, comptée par le limiteur (IP réelle du navigateur).
   - C) Servie, avec `customRules: false`.
   - **Recommandé : A** : aucun consommateur ; supprime la fuite du jeton et le coût du limiteur.
3. **Q3 Jeton dans `/sign-in/email`, `/sign-up/email` et `/magic-link/verify`** : le retirer par hook `after`, dans cette tâche. **Recommandé : oui** : même classe de fuite, coût faible.
4. **Q4 Sentry.**
   - A) `connect-src` avec l'origine exacte tirée du DSN de build.
   - B) `tunnelRoute: "/monitoring"`, exclu du matcher.
   - C) Joker `*.ingest.de.sentry.io`.
   - **Recommandé : A.** B ajoute du trafic serveur et une route publique, utiles seulement contre les bloqueurs de publicité. C est refusé (exfiltration).
5. **Q5 Rendu et nonce.**
   - A) `await connection()` dans le layout racine.
   - B) `connection()` page par page.
   - C) SRI expérimentale : ne couvre pas les scripts en ligne de Next.
   - D) Sans nonce : impose `unsafe-inline`, interdit.
   - **Recommandé : A.**
6. **Q6 Styles.**
   - A) `style-src 'self' 'nonce-…'` et `style-src-attr 'unsafe-inline'`.
   - B) `style-src 'self' 'unsafe-inline'`.
   - C) Strict : casse `next/image` et Magic UI.
   - **Recommandé : A** : les éléments `<style>` restent sous nonce. SECURITY §3 n'interdit `unsafe-inline` que pour les scripts.
7. **Q7 HSTS** : `max-age=63072000; includeSubDomains`, sans `preload`. **Recommandé : oui** ; `preload` (quasi irréversible) en P10-02.
8. **Q8 Referrer-Policy.**
   - A) `strict-origin-when-cross-origin`.
   - B) `same-origin`.
   - C) `no-referrer` : envoie `Origin: null` en POST ; toléré par Better Auth grâce à `sec-fetch-site`, mais fragile.
   - **Recommandé : A**, avec `noreferrer` lien par lien vers les offres en P6.
9. **Q9 Permissions-Policy** : la liste de D1. **Recommandé : telle quelle** ; `payment` à rouvrir en P9 si Stripe Elements.
10. **Q10 Rapport de violations CSP (`report-to` vers Sentry)** : maintenant ou en P10-02. **Recommandé : P10-02.** Ces rapports échappent à `beforeSend` (URL du document, quota) ; l'E2E sert de garde d'ici là.
11. **Q11 « Déjà connecté »** : `redirectIfSignedIn` (par `decideAccess`) sur `/connexion` et `/inscription`. **Recommandé : oui**, dans la page, jamais dans le proxy.
12. **Q12 `requestId`** : généré par le proxy, valeur entrante écrasée, renvoyé en réponse, autorisé dans Sentry. **Recommandé : oui.**
13. **Q13 ADR 0016** « En-têtes de sécurité, CSP à nonce et rôle de `proxy.ts` » : rendu dynamique, lecture de session dans le proxy, `/get-session` fermée, origine Sentry. **Recommandé : oui.**
14. **Q14 E2E avec accès direct à la base E2E** pour vieillir une session (`tests/e2e/base.ts`, boucle locale). **Recommandé : oui** : seule preuve de la prolongation dans le vrai runtime Next.
