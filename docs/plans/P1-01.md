## 2. Schéma (`db/schema.ts`, fichier unique selon `rules/db.md`)

### Conventions
- **Noms SQL explicites en snake_case** dans chaque colonne (`text("external_id")`), sans option `casing`. Le SQL généré se lit directement, et rien ne peut diverger entre la config drizzle-kit et le client. Better Auth, lui, se sert des clés TS (`emailVerified`).
- **Identifiants** : `uuid("id").primaryKey().defaultRandom()` → `gen_random_uuid()`, natif depuis PG 13 (Neon 14 à 18). ARCHITECTURE §9 parle déjà d'un « `userId` (UUID interne) ».
- **Horodatages** : `timestamp(..., { withTimezone: true, mode: "date" })`, `created_at default now() not null`. `updated_at` suit `.$onUpdate(() => new Date())`, et il est **posé explicitement dans chaque `onConflictDoUpdate`**, car `$onUpdate` ne couvre pas le `set` d'un upsert.
- **Tableaux** : `text[] not null default '{}'`.
- **Montants** : `numeric(10,6)`, renvoyé en chaîne par `pg`.
- **Enums** : `pgEnum`, dont les valeurs viennent de tuples `as const` dans `src/lib/db/enums.ts` (fichier sans dépendance Drizzle). Les schémas Zod les réutilisent (`z.enum(CONTRACT_TYPES)`) sans importer `pg-core` côté client.

### Tables

**`users`** (table utilisateur de Better Auth ; `modelName: "users"` en P1-02)
- Colonnes : `id uuid pk`, `name text not null`, `email text not null`, `email_verified boolean not null default false`, `image text`, `role user_role not null default 'user'`, `plan plan not null default 'free'`, `created_at`, `updated_at`.
- Contraintes : `unique(email)` ; `check (email = lower(email))`. Le seed met l'email en minuscules ; P1-02 devra vérifier que Better Auth le fait aussi.
- *Écart §5* : `email_verified`, `image` et `updated_at` sont ajoutés parce que Better Auth les exige.

**`search_profiles`**
- Clé : `user_id uuid pk → users.id on delete cascade` (« 1 par user » : la clé primaire suffit).
- Colonnes : `titles text[]`, `skills text[]`, `years_exp smallint`, `languages text[]`, `zone text not null`, `remote_modes work_mode[] not null default '{onsite,hybrid,remote}'`, `contracts contract_type[] not null default '{}'`, `min_salary integer`, `excluded_keywords text[]`, `excluded_companies text[]`, `threshold smallint not null default 60`, `channels jsonb not null default '{}'`, `send_hour smallint not null default 7`, `frequency digest_frequency not null default 'daily'`, `created_at`, `updated_at`.
- Checks : `threshold between 0 and 100` (PRD F4), `send_hour between 0 and 23`, `years_exp between 0 and 60`, `min_salary >= 0`.
- *Écarts §5* :
  - `remote_mode` devient le tableau **`remote_modes`**. Kwasi accepte « tous modes de travail » ; un tableau évite une valeur `any` absente des offres.
  - `min_salary` : salaire **brut annuel en euros**, documenté.
  - `send_hour` : heure locale **Europe/Brussels**, sans colonne de fuseau (YAGNI, utilisateurs belges).
  - `zone` : texte libre (« Namur »). Son format réel sera tranché par P2-00 et P2-02 à P2-04, avec une migration additive.
  - `channels` : forme validée par Zod `{ telegram?: { enabled: boolean }, email?: { enabled: boolean } }`. Le `chat_id` Telegram relève de P4-02.

**`job_offers`**
- Colonnes : `id uuid pk`, `source job_source not null`, `external_id text not null`, `dedup_hash text not null`, `canonical_offer_id uuid null → job_offers.id on delete set null`, `title text not null`, `company text`, `location text`, `contract contract_type`, `salary_min integer`, `salary_max integer`, `remote work_mode`, `description text not null default ''`, `url text not null`, `published_at timestamptz`, `raw jsonb not null`, `created_at`, `updated_at`.
- Contraintes : `unique(source, external_id)` (idempotence de la collecte).
- Index :
  - `index(dedup_hash)` (§5) ;
  - `index(canonical_offer_id) where canonical_offer_id is not null` (index de la clé étrangère) ;
  - index partiel `(published_at desc) where canonical_offer_id is null` : le job ne lit que les offres canoniques.
- Checks :
  - `canonical_offer_id <> id` ;
  - `dedup_hash ~ '^[0-9a-f]{64}$'` (sha256 hexadécimal) ;
  - `salary_min <= salary_max` si les deux sont présents ;
  - salaires `>= 0` ;
  - `url ~ '^https?://'`.
- Hors de portée d'une contrainte : l'absence de chaîne de canoniques (une canonique qui pointerait elle-même vers une autre). La règle est applicative, en P2-05 et P2-06.

**`offer_scores`**
- Clé : `pk(user_id, offer_id)`, qui assure le `unique` de §5. `user_id → users cascade`, `offer_id → job_offers cascade`.
- Colonnes : `score smallint`, `strengths text[]`, `concerns text[]`, `reason text`, `status score_status not null`, `model text not null`, `prompt_version text not null`, `input_tokens integer`, `output_tokens integer`, `cost_usd numeric(10,6)`, `created_at`.
- Checks : `score between 0 and 100` ; `(status = 'scored') = (score is not null)` ; tokens et coût `>= 0`.
- Index : `index(offer_id)`, pour que la cascade venant de `job_offers` ne balaie pas toute la table.

**`offer_feedback`**
- Clé : `pk(user_id, offer_id)`, mêmes clés étrangères en cascade.
- Colonnes : `verdict feedback_verdict not null`, `created_at`.
- Index : `index(offer_id)`.

**`applications`**
- Colonnes : `id uuid pk`, `user_id → users cascade`, `offer_id → job_offers` **`on delete restrict`**, `status application_status not null default 'to_review'`, `applied_at timestamptz`, `notes text`, `created_at`, `updated_at`.
- Contraintes et index : `unique(user_id, offer_id)`, `index(offer_id)`.
- *Motif du `restrict`* : une purge future des offres (SECURITY §4, « offres brutes 90 jours ») ne doit pas effacer en silence l'historique de candidatures.

**`deliveries`**
- Colonnes : `id uuid pk`, `user_id → users cascade`, `channel delivery_channel not null`, `digest_date date not null` (mode chaîne, date à Bruxelles), `offer_ids uuid[] not null default '{}'`, `status delivery_status not null default 'pending'`, `error text`, `created_at`, `sent_at timestamptz`.
- Contrainte : `unique(user_id, channel, digest_date)`.
- Check : `cardinality(offer_ids) <= 10` (ARCHITECTURE §6 : 10 offres au plus par digest).
- `error` : un code ou un message nettoyé, sans PII (règle à appliquer en P4).

**`job_runs`**
- Colonnes : `id uuid pk`, `kind job_run_kind not null`, `started_at timestamptz not null default now()`, `finished_at timestamptz`, `status job_run_status not null default 'running'`, `stats jsonb not null default '{}'`.
- Check : `finished_at >= started_at`.
- Index : `(kind, started_at desc) where status = 'succeeded'`, pour « collecte depuis le dernier run réussi » (§6).

**Types exportés** : `User`, `NewUser`, `SearchProfile`, … (`$inferSelect` / `$inferInsert`).

**Invariant RGPD** (P7-04, contrôlé par un test) : toute table qui porte `user_id` a une clé étrangère vers `users` **en cascade** et un index ou une clé primaire qui **commence** par `user_id`. Cela rend la suppression de compte effective et donne aux requêtes scopées de P1-03 un index.

### Tables Better Auth (`sessions`, `accounts`, `verifications`) : laissées à P1-02
Recommandation : **en P1-01, seulement `users` compatible avec Better Auth. Les trois autres tables sont générées en P1-02** par `@better-auth/cli generate` depuis la vraie configuration, puis ajoutées par une migration additive.

Motifs :
- ARCHITECTURE §5 les dit « gérées par la bibliothèque ».
- Leur forme dépend des choix de P1-02 : lien magique, plugin `admin` (qui ajoute `banned`, `ban_reason`… à `users` et `impersonated_by` à `session`), stockage du rate limit de P1-04.
- Les écrire maintenant, ce serait deviner, avec le risque d'une migration corrective.

Conséquence à accepter : « schéma complet » s'entend « tables métier complètes + `users` ». Voir Q2.

## 3. Client DB, migrations, configuration

### Fichiers et signatures clés
- **`src/lib/db/enums.ts`** : tuples `as const` (`CONTRACT_TYPES`, `WORK_MODES`, …).
- **`src/lib/db/client.ts`**
  ```ts
  export type Database = NodePgDatabase<typeof schema>;
  export function createPool(url: string, options: { applicationName: "trouvio-web" | "trouvio-job" | "trouvio-cli"; max?: number }, log?: Logger): Pool;
  export function createDatabase(pool: Pool): Database;
  export function getDb(): Database;          // paresseux : aucune connexion à l'import (le build n'exige rien)
  export async function closeDb(): Promise<void>;
  ```
  - Réglages du pool : `max` 10 par défaut, `connectionTimeoutMillis: 5000`, `idleTimeoutMillis: 30000`, `application_name`.
  - **`pool.on("error")` → `logger.error(..., { source: "db", err })`**. Sans ce gestionnaire, une connexion inactive coupée par Neon fait tomber le processus.
- **`src/lib/db/migrate.ts`** : `runMigrations(pool: Pool, migrationsFolder = MIGRATIONS_FOLDER): Promise<{ applied: number }>`.
  - Il enveloppe `migrate()` de `drizzle-orm/node-postgres/migrator` et compte les lignes de `drizzle.__drizzle_migrations` avant et après.
  - Le même code sert au CLI, au globalSetup des tests et, plus tard, au conteneur (P10-02).
- **`src/lib/db/target.ts`** : `describeTarget(url): "base locale" | "base distante"` et `isLoopback(url)`. On n'affiche **jamais** l'hôte, l'utilisateur ni le mot de passe.
- **`drizzle.config.ts`** (racine) : `dialect: "postgresql"`, `schema: "./db/schema.ts"`, `out: "./db/migrations"`, `strict: true`, `verbose: true`, **sans `dbCredentials`**.
  - drizzle-kit ne sert qu'à `generate` et `check`, qui ne se connectent pas. La config ne lit donc aucune variable et tourne dans le bac à sable comme en CI.
- **ESLint** : ajouter `lib/db` au motif « code client ou isomorphe » (même mécanisme que `env` et `logger`). Aucun composant client ne doit importer `pg`.

### Variables (`src/lib/env.ts`, `.env.example`, ARCHITECTURE §8)
| Domaine | Variable | Règle |

## 4. Seed

- **Format** de `db/seed.example.json`, commité, fictif, emails en `example.com` :
  ```json
  { "users": [ { "email": "alex.martin@example.com", "name": "Alex Martin", "role": "admin", "plan": "free",
      "profile": { "titles": ["Développeur full-stack"], "skills": ["TypeScript","React","PostgreSQL"], "yearsExp": 5,
        "languages": ["fr","en"], "zone": "Namur", "remoteModes": ["hybrid","remote"], "contracts": ["permanent","freelance"],
        "minSalary": 45000, "excludedKeywords": ["stage"], "excludedCompanies": [], "threshold": 60,
        "channels": { "telegram": { "enabled": true }, "email": { "enabled": false } }, "sendHour": 7, "frequency": "daily" } } ] }
  ```
- **Validation Zod** :
  - `src/features/profile/core/search-profile.ts` exporte `searchProfileSchema` (objet strict, bornes identiques aux checks SQL, `languages` en ISO 639-1, tableaux ≤ 50 éléments dédoublonnés et nettoyés des espaces). P6-05 le réutilisera.
  - `src/lib/db/seed/seed-file.ts` exporte `seedFileSchema` : `users` de 1 à 20 éléments, email en minuscules par `transform`, emails distincts (`superRefine`), et `parseSeedFile(json: unknown): SeedFile`.
  - **Les erreurs ne citent que des chemins** (`users.0.profile.threshold`), jamais la valeur : le fichier local contient des prétentions salariales.
- **Garde** (`src/lib/db/seed/guard.ts`) : `assertSeedAllowed({ nodeEnv, databaseUrl, allowRemote })`.
  - Refus si `NODE_ENV=production`.
  - Refus d'un hôte hors boucle locale sans `--allow-remote`.
  - Message sans URL.
- **Application** (`src/lib/db/seed/apply.ts`) : `applySeed(db, seed): Promise<{ users: number; profiles: number }>`.
  - Une transaction.
  - Upsert `users` sur `email` (`onConflictDoUpdate` : `name`, `role`, `plan`, `updated_at`), puis upsert `search_profiles` sur `user_id`.
  - Idempotent.
  - N'efface rien : un utilisateur retiré du fichier reste en base, ce qui est documenté.
- **CLI** (`src/lib/db/seed/cli.ts`) :
  - `--file <chemin>`, défaut `db/seed.local.json`. Si le fichier manque : message « copie `db/seed.example.json` vers `db/seed.local.json` ».
  - `--allow-remote`.
  - Journalise les comptes seulement.
  - Code de sortie par `process.exitCode`.
- **Où il tourne** :
  - Claude, sur Docker, avec `--file db/seed.example.json`.
  - L'utilisateur, sur Neon, avec son `seed.local.json` réel (le vrai profil pour M1).

## 5. Base de dev et de test non secrète : recommandation

### Variantes évaluées
| Variante | Joignable depuis le bac à sable | Si Claude obtient des droits SQL élevés | Parité CI et Neon | Verdict |
|---|---|---|---|---|
| **Postgres.app** (déjà installé, PG 18), serveur lancé hors bac à sable par l'utilisateur | oui en TCP `127.0.0.1` (socket Unix : EPERM) | le serveur tourne **sous le compte macOS de l'utilisateur, hors bac à sable**. Un rôle superutilisateur ou `pg_execute_server_program` permet `COPY … TO PROGRAM` et `pg_read_file` : **lecture de `.env.local` et de `~` hors bac à sable**. `trust` par défaut, et permission mémorisée par application | version au choix ; pas d'image commune avec la CI | écartée |
| **Docker** (Docker Desktop installé), conteneur lancé par l'utilisateur, publié sur `127.0.0.1:54329` | oui (TCP boucle locale, mesuré permis) | l'exécution côté serveur reste **dans le conteneur** : volume nommé, aucun montage de l'hôte hors `init.sql` en lecture seule | **même image, épinglée par digest, en local et en service CI** ; version alignée sur Neon | **retenue** |
| **PGlite** (WASM en processus, tests seulement) | oui, sans serveur | aucune surface serveur | autre pilote (`drizzle-orm/pglite`), contraire à ADR 0002 (« tests identiques à la production » avec `pg`) ; une seule connexion, donc pas de test du verrou concurrent de P5-01 ; contraire à `rules/db.md` (« conteneur ou branche Neon ») | écartée |
| **Branche Neon dédiée aux tests** | non (`*.neon.tech` refusé ; aurait besoin d'un secret) | — | parfaite | écartée pour Claude (P0-08 : aucun secret dans le bac à sable) |

### Décision proposée (à consigner dans un nouvel **ADR 0012**, qui ferme le point laissé ouvert par ADR 0011 §6)

1. **Postgres local = conteneur Docker** `db/local/compose.yaml`.
   - Image `postgres:<majeure de Neon>-alpine@sha256:…`.
   - `ports: "127.0.0.1:54329:5432"` : **jamais `0.0.0.0`**, que Docker Desktop exposerait au réseau local. Le port 54329 évite le serveur qui écoute déjà sur 5432.
   - Volume nommé `trouvio-pg`, `restart: unless-stopped`, `healthcheck: pg_isready`.
   - `db/local/init.sql`, monté en lecture seule, crée le rôle **`trouvio` NOSUPERUSER CREATEDB** (mot de passe jetable `trouvio`) et la base `trouvio_dev` dont il est propriétaire. Parité avec Neon, où le propriétaire n'est pas superutilisateur : une migration qui exigerait un superutilisateur échoue dès le poste.
   - Le superutilisateur `postgres` du conteneur a un mot de passe jetable et ne sert qu'à l'initialisation.
2. **Variables non secrètes** dans `db/local/dev.vars` (nom **non `.env*`**, commité, lisible par le bac à sable) : `DATABASE_URL` et `DATABASE_MIGRATION_URL` = `postgres://trouvio:trouvio@127.0.0.1:54329/trouvio_dev`. C'est l'option B de P0-08, sans générateur (les valeurs ne sont pas secrètes). `TEST_DATABASE_URL` n'y figure pas : son défaut suffit.
3. **Tests d'intégration** (projet Vitest `db`, fichiers `*.db.test.ts`) :
   - le `globalSetup` crée `trouvio_test_tpl_<pid>_<rand>`, y applique `runMigrations`, puis ferme sa connexion ;
   - chaque fichier clone sa base (`CREATE DATABASE … TEMPLATE …`) : bases isolées, en parallèle sans risque ;
   - le démontage fait `DROP DATABASE … WITH (FORCE)` ;
   - le test « base vierge » part d'une base **vide**, pas du modèle ;
   - base injoignable : erreur claire « Base de test injoignable sur 127.0.0.1:54329 : lance `pnpm db:local:up` dans ton terminal », jamais de `skip`.
4. **Qui fait quoi** :

| Où | Quoi |
|---|---|
| **Utilisateur (terminal)** | `pnpm db:local:up` une fois (Docker est incompatible avec le bac à sable, et `docker *` est en `ask`). Sur Neon : rôle applicatif, sauvegarde avant migration, `pnpm db:migrate:neon`, `pnpm db:seed:neon -- --allow-remote` avec `.env.local` |
| **Claude (bac à sable)** | `pnpm db:generate`, `db:check`, `db:migrate:local`, `db:seed:local -- --file db/seed.example.json`, `pnpm test` / `verify`, tout en TCP vers `127.0.0.1:54329` ; aucun secret |
| **CI (`quality`)** | service `postgres` (même image et même digest, `ports: 54329:5432`, `POSTGRES_PASSWORD` jetable), étape `psql … -f db/local/init.sql` (psql est présent sur ubuntu-24.04), puis `pnpm verify` inchangé (URL de test par défaut, `db:check` compris). `e2e` inchangé jusqu'à P1-02 |

5. **Neon (dev, puis prod en M1)**, terminal de l'utilisateur, **dans cet ordre** :
   1. Choisir ou confirmer la majeure du projet Neon (Q1).
   2. SQL Neon, dans l'éditeur, avec le propriétaire : `CREATE ROLE trouvio_app LOGIN PASSWORD …` (un rôle créé **en SQL** ne reçoit pas `neon_superuser`, contrairement à la console), `GRANT USAGE ON SCHEMA public`, `ALTER DEFAULT PRIVILEGES FOR ROLE <propriétaire> IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO trouvio_app`. **Avant** la migration, pour que les privilèges par défaut s'appliquent aux nouvelles tables.
   3. `.env.local` : `DATABASE_URL` (trouvio_app, `sslmode=require`) et `DATABASE_MIGRATION_URL` (propriétaire).
   4. Branche Neon `pre-p1-01` (retour arrière instantané).
   5. `pnpm db:migrate:neon`, puis `pnpm db:seed:neon -- --allow-remote`.
   6. Contrôle de moindre privilège : connecté en `trouvio_app`, `CREATE TABLE t()` échoue et `SELECT count(*) FROM users` réussit.
   7. L'utilisateur colle dans la conversation **la sortie des commandes seulement** (aucune URL n'y est imprimée).

### Constat de sécurité à traiter tout de suite (hors code, décision de l'utilisateur)
**Un serveur écoute sur `127.0.0.1:5432` et le bac à sable l'atteint** (mesuré).

- Si c'est Postgres.app en `trust`, et qu'une permission a déjà été accordée à l'application cliente (node, terminal), du code confiné pourrait se connecter en superutilisateur. Il lirait alors `.env.local` ou `~` par `COPY … FROM PROGRAM` : **franchissement de la frontière d'ADR 0011**.
- Le résiduel d'ADR 0011 (« sortie vers tout port localhost ») ne couvre pas ce cas, qu'il faut ajouter à l'ADR 0012 et à SECURITY §7.
- Actions pour l'utilisateur, dans son terminal :
  1. identifier le processus : `lsof -nP -iTCP:5432 -sTCP:LISTEN` ;
  2. si c'est Postgres.app : l'arrêter quand il ne sert pas, ou passer son `pg_hba.conf` en `scram-sha-256`, et vider ses permissions (« Reset App Permissions ») ;
  3. aucun réglage du bac à sable ne filtre un port localhost précis (le proxy ne voit pas ce trafic).
- La sonde n'a fait qu'une ouverture TCP, sans authentification : rien n'a été lu.

## 8. Risques, retour arrière, sécurité

- **Migration non destructive** : uniquement des `CREATE TYPE`, `CREATE TABLE` et `CREATE INDEX`, sur une base vide. Le migrateur 0.45 applique tout dans **une** transaction : un échec ne laisse rien de partiel.
- **Retour arrière** :
  - en local : `pnpm db:local:down` puis `docker volume rm` ;
  - sur Neon : restauration de la branche `pre-p1-01`, ou `DROP SCHEMA public CASCADE; CREATE SCHEMA public; DROP SCHEMA drizzle CASCADE;` (la base ne contient rien d'autre) ;
  - côté code : revert de la PR ; après application sur Neon, toute correction passe par une nouvelle migration.
- **Dérive schéma ↔ migrations** : `db:check` en CI.
- **Migrations concurrentes** : peu probable (un seul opérateur). Pas de verrou consultatif ici ; P5-01 l'ajoutera au job.
- **Friction** : `pnpm test` et `verify` exigent désormais Docker lancé, dans le bac à sable comme dans le terminal. Le message est explicite et il n'y a pas de `skip`.
- **Drizzle v1** : en restant sur 0.45, une montée ultérieure imposera de convertir le dossier de migrations (`drizzle-kit up`). Accepté (Q4).
- **Tables Better Auth plus tard** : P1-02 ajoute une migration additive ; `users` est déjà compatible.

**Checklist SECURITY §5**
| Point | Statut |
|---|---|
| Auth et appartenance | sans objet (aucune route) ; l'invariant `user_id` indexé et en cascade prépare P1-03 |
| Entrées validées par Zod, erreurs sans détail | seed et env : chemins et noms seulement |
| Aucun secret ni PII dans le code, les logs, les messages | seed réel hors dépôt ; exemple fictif ; identifiants locaux jetables en boucle locale (acceptés par `litteraux-secrets`) ; aucune URL imprimée |
| Contenu externe non fiable | `raw jsonb` stocké tel quel, jamais rendu |
| Drizzle, pas de SQL concaténé | oui ; les checks utilisent `sql` tagué |
| Rate limiting, coût IA | sans objet |
| Tests négatifs | §6 : bornes, refus, cascades, restrict, garde production, URL distante refusée |

## 9. Questions ouvertes, chacune avec une recommandation

- **Q1. Majeure Postgres.** Le projet Neon existe-t-il déjà, et en quelle version ?
  - *Recommandé* : **PG 18** si le projet est à créer (version courante, prise en charge par Neon, et celle de Postgres.app sur le poste) ; sinon la majeure existante.
  - L'image Docker et le service CI suivent cette majeure. Les ids restent en `gen_random_uuid()` quelle que soit la version.
- **Q2. Tables Better Auth.** *Recommandé* : **en P1-02**, générées par la CLI Better Auth. P1-01 livre `users` compatible et les tables métier. Motifs au §2 : forme dépendante des plugins, « gérées par la bibliothèque ». La ROADMAP porte une note dans ce sens.
- **Q3. Rôle propriétaire vs rôle applicatif.** `.env.example` décrit `DATABASE_URL` comme le rôle applicatif sans DDL, alors que la migration exige du DDL : contradiction à trancher.
  - *Recommandé* : nouvelle variable **`DATABASE_MIGRATION_URL`**, lue seulement par `db:migrate` ; le rôle `trouvio_app` est créé en SQL avant la première migration (§5.5).
  - Le job GitHub (P5-02) n'aura jamais l'URL propriétaire.
- **Q4. Drizzle 0.45 stable ou 1.0 RC.** *Recommandé* : **0.45.3 / 0.31.11**. Ce sont les versions `latest`, la RC ne bouge plus depuis juin, et Better Auth accepte les deux. Le projet évite les pré-versions (`trustPolicy`, `minimumReleaseAge`).
- **Q5. `db/seed.local.json` lisible par Claude.** Ce n'est pas un secret, mais il contient des données personnelles (prétentions salariales).
  - *Recommandé* : **le refuser** : `denyRead` et `Read(./db/seed.local.json)` en deny dans `.claude/settings.json`, fichier que seul l'utilisateur peut modifier. Claude n'en a pas besoin et utilise l'exemple (minimisation RGPD). Le hook `guard-files` pourrait aussi le couvrir en filet.
- **Q6. Serveur déjà en écoute sur `127.0.0.1:5432`.** *Recommandé* : l'identifier maintenant (`lsof`, §5). Si c'est Postgres.app : l'arrêter hors usage, ou passer en `scram-sha-256` et réinitialiser ses permissions. Consigner le résiduel dans l'ADR 0012 et SECURITY §7.
- **Q7. Docker vs Postgres.app pour la base de Trouvio.** *Recommandé* : **Docker**. L'exécution côté serveur reste confinée au conteneur, l'image est la même qu'en CI, et le rôle non superutilisateur donne la parité avec Neon. Postgres.app ferait tourner le serveur avec les droits du compte de l'utilisateur, hors bac à sable.
- **Q8. Rétention des offres (SECURITY §4, « 90 jours »).** Aucune tâche de la ROADMAP ne purge les offres.
  - *Recommandé* : ajouter une tâche en P5 ou P7, qui purgerait `raw` ou les offres non référencées. Le `restrict` de `applications.offer_id` protège déjà l'historique.
- **Q9. Codes d'enums en anglais.** Exemples : `permanent`/`fixed_term` plutôt que `cdi`/`cdd`, `free`/`economy`/`comfort`.
  - *Recommandé* : anglais, cohérent avec `to_review`/`not_relevant` déjà fixés dans §5. Les libellés français vivent dans l'interface.

### Décisions (validées par l'utilisateur le 2026-10-01 : toutes les recommandations)
- **Q1** : PG 18 si le projet Neon est à créer, sinon la majeure existante ; l'image Docker et le service CI suivent. Le 2026-10-01 : aucun projet Neon encore créé → **PG 18** (le projet Neon sera créé en 18).
