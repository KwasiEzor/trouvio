# P0-02 — `src/lib/env.ts` : validation Zod de l'environnement

**Statut** : validé (2026-09-27) · **Date** : 2026-09-27 · **Branche** : `chore/P0-02-env-validation` · Plan produit par l'agent `architect`.

## Objectif et critères d'acceptation
« `src/lib/env.ts` : validation Zod de toutes les variables (`.env.example` à jour). *Accept.* : démarrage refusé si une variable requise manque, test unitaire à l'appui. »
Sens retenu : toutes les variables prévues par les docs sont **déclarées** (groupées par domaine) ; sont **requises au démarrage** celles des domaines déjà en service pour ce runtime ; le serveur (`next start`) et le futur CLI du job refusent de démarrer en listant les **noms** fautifs, jamais les valeurs.

## Versions (vérifiées le 2026-09-27, registre npm)
`zod` 4.6.5 · `vitest` 5.0.2 · `vite` 8.3.1 (dépendance de Vitest 5 **non optionnelle**, à déclarer). Pas de `@t3-oss/env-nextjs` (0.13, pré-1.0, validation d'un bloc sans domaines ni runtimes).

## Décisions
1. **Contradiction d'ordre** (test exigé, Vitest prévu en P0-03) → **P0-02 installe Vitest minimal** (`vitest.config.ts` node, `pnpm test`, `test` ajouté à `verify`) ; P0-03 garde Testing Library, MSW, Playwright et la couverture. ROADMAP P0-02/P0-03 reformulées en conséquence.
2. **Schéma complet, validation par domaine, domaines requis selon le runtime** : `STARTUP_DOMAINS = { web: ["core"], job: ["core"] }` aujourd'hui ; chaque tâche future ajoute son domaine (un test l'oblige à le faire exprès). Le build n'exige rien (`register()` n'est pas appelé pendant `next build`, vérifié dans le code de Next) → la CI n'a besoin d'aucun secret. Pas d'interrupteur `SKIP_ENV_VALIDATION`.
3. **`APP_URL`** requise en production, `http://localhost:3000` par défaut en dev/test → `pnpm dev` marche sans secret, `next start` sans `APP_URL` refuse de démarrer.
4. **Validation au démarrage** dans `src/instrumentation.ts` (`register()` → `assertStartupEnv("web")`) ; CLI du job (P5-01) : première ligne de `scripts/job-run.ts`. Jamais dans `next.config.ts` (le build exigerait des secrets).
5. **Pas de `server-only`** (lève une erreur hors `react-server` : casserait Vitest et le CLI) → garde `typeof window` + test qu'aucune variable serveur n'est `NEXT_PUBLIC_*`.
6. **Erreurs** : `EnvValidationError { issues: { name, reason: "manquante" | "invalide" }[] }`, message du type `Configuration invalide (web) — manquantes : APP_URL ; invalides : DATABASE_URL`, sans `cause` (on ne transporte pas l'erreur Zod).
7. **`.env.example`** : valeurs de secrets **vides**, seules valeurs non secrètes remplies (`APP_URL`, `ANTHROPIC_MODEL_SCORING`) ; commentaires : phase où la variable devient requise, où obtenir la clé, format. Écrit avec l'outil Write ; `.env.local` jamais lu ni créé par Claude.
8. **Interdit `process.env` étendu** (reporté de P0-01) : ESLint couvre `src/`, `scripts/**/*.ts`, `db/`, `evals/**/*.ts`, `tests/` (sauf `src/lib/env.ts`), y compris `globalThis.process.env`, `process["env"]`, déstructuration et `import { env } from "node:process"`. Les `*.config.*` racine restent hors périmètre (outillage). Le hook `guard-code.sh` est aligné (modification = confirmation humaine).

## Tests prévus (écrits avant le code)
- **Nominaux** : `core` valide → objet typé ; valeurs par défaut (`NODE_ENV`, `APP_URL` hors production, modèle) ; chaque domaine accepte une fixture complète et ne renvoie que ses clés.
- **Limites** : chaîne vide ou espaces = absente ; trim ; clés inconnues ignorées ; erreurs multi-domaines agrégées et triées ; `STARTUP_DOMAINS` exactement `{ web: ["core"], job: ["core"] }`.
- **Négatifs** : production sans `APP_URL` → « manquante » ; URL invalide, `ftp://`, `NODE_ENV=staging`, `DATABASE_URL=mysql://…`, secret trop court, modèle `gpt-4o` → « invalide » ; `assertStartupEnv` ; lecteur paresseux (rien validé à la création, erreur au premier accès, source lue une seule fois).
- **Sécurité** : valeurs sentinelles absentes de `message`, `String(err)`, `stack`, `JSON.stringify(err)`, `issues` ; `cause` indéfinie ; aucune variable serveur `NEXT_PUBLIC_*` ; `getEnv` refusé côté navigateur ; `.env.example` synchronisé avec les schémas (chaque clé présente, aucune inconnue, aucune valeur non vide hors liste blanche).
- **Hooks** : `process.env` refusé dans `scripts/`, `db/`, tests, `globalThis.process.env`, `process["env"]`, déstructuration, import depuis `node:process` ; autorisé dans `src/lib/env.ts`, `const { argv } = process`, `vitest.config.ts`.
- **Démarrage réel** : `pnpm build` sans secret ; `APP_URL= pnpm start` → code 1, stderr cite `APP_URL` sans valeur ; avec `APP_URL` → HTTP 200.

## Risques et questions
- Chaque tâche future doit ajouter son domaine à `STARTUP_DOMAINS` (règle écrite dans ARCHITECTURE, test qui l'impose).
- Le lien magique (P1-02) pourrait exiger le domaine `email` dès P1-02 : tranché au plan de P1-02.
- Migrations avec un rôle propriétaire distinct (`DATABASE_MIGRATION_URL`) : décidé en P1-01.
- En dev, une erreur dans `register()` ne coupe peut-être pas le serveur : critère prouvé en `next start` et par les tests ; comportement en dev noté.
- Vitest 5 a trois semaines : repli sur 4.1.11 si incompatibilité.
- CLI du job en CI (P5-02) : poser `NODE_ENV=production` dans le workflow.
